Test Workflows

Test Workflows sind der zentrale Baustein für automatisiertes Testen in Autemos. Sie bieten eine visuelle, node-basierte Darstellung der Testlogik, die es Benutzern ermöglicht, automatisierte Tests effizient zu entwerfen, anzupassen und zu debuggen.

Ein typischer Workflow besteht aus aufeinanderfolgenden Schritten wie dem Öffnen einer Anwendung, der Interaktion mit UI-Elementen, der Validierung von Ergebnissen und der Datenverwaltung. Während die meisten Workflows linear sind, unterstützt Autemos auch bedingte Logik und Schleifen für fortgeschrittenere Testszenarien.

Die Test Workflows Übersicht listet alle vorhandenen Tests mit Listen-/Kachelansicht und Suchoptionen auf.

Was Sie mit Test Workflows tun können

  • Aufgezeichnete Tests verfeinern und benutzerdefinierte Logik hinzufügen
  • Validierungen und Assertions hinzufügen, um das Anwendungsverhalten zu überprüfen
  • Testdaten für dynamische, wiederverwendbare Szenarien integrieren
  • Ausführung Schritt für Schritt mit Breakpoints und Live-Ansicht debuggen
  • Testbereitschaft vor der automatisierten Headless-Ausführung sicherstellen
Die visuelle Canvas — jeder Schritt wird als Node dargestellt, der eine bestimmte Aktion ausführt.

Erstellen und Bearbeiten

Die Test Workflows Übersicht listet alle vorhandenen Tests auf. Die Schaltfläche + New Workflow öffnet eine leere Canvas. Die Schaltfläche Record Workflow navigiert zum Aufzeichnungsmodul, in dem Tests mit einem Klick-Recorder oder einem KI-Chatbot erstellt werden können. Workflows können zwischen Listen- und Kachelansicht umgeschaltet, gesucht, sortiert und ausgewählt werden.

Jeder Schritt im Workflow wird durch einen Node dargestellt, der eine bestimmte Aktion ausführt, wie z. B. das Klicken auf ein Element, die Texteingabe oder die Validierung einer Bedingung.

Kernkonzepte

Lineare Ausführung

Die meisten Workflows folgen einer von oben nach unten ausgeführten Abfolge von Schritten.

Bedingte Logik

Verwenden Sie If-Nodes, um die Ausführung basierend auf Laufzeitbedingungen zu verzweigen.

Schleifen

Iterieren Sie über Daten oder wiederholen Sie Aktionen mit Loop-Nodes für datengetriebenes Testen.

Drag & Drop Bearbeitung

Nodes können direkt auf der visuellen Canvas hinzugefügt, entfernt und umsortiert werden.

Beispiel: Bedingte Logik mit einem If-Node zur Verzweigung der Ausführung.

Nodes verstehen

Nodes sind die grundlegenden Einheiten eines Test Workflows. Jeder Node repräsentiert eine einzelne Aktion oder Operation:

  • Interaktion mit UI-Elementen (Click, Type)
  • Informationen erfassen (Extract Text, Screenshot)
  • Verhalten validieren (Assert, Soft Verify)
  • Daten verwalten (Test Data, Input-Variablen)
  • Ablauf steuern (If, Loop, Wait)

Nodes können je nach Typ mit Variablen und gespeicherten Daten interagieren. Eine detaillierte Dokumentation für jeden Node ist in den Node-Referenzabschnitten weiter unten verfügbar.

Node-Panel — verfügbare Node-Kategorien

Mit Testdaten und Variablen arbeiten

Test Workflows unterstützen eine flexible Datenverwaltung für dynamische und wiederverwendbare Tests. Daten können in Variablen gespeichert, während der Ausführung zwischengespeichert und in späteren Schritten wiederverwendet werden.

  • Werte in Workflow-Variablen speichern und schrittübergreifend wiederverwenden
  • Den Test Data Easy-Node verwenden, um tabellarische Datensätze inline zu binden
  • Auf Zeilendaten zugreifen über {{easyData.field}} oder {{easyDataRecords.0.field}}
  • Extern verwaltete Datensätze für die workflow-übergreifende Wiederverwendung verknüpfen
Test Data Easy — Datensatz direkt im Workflow binden.

Unterstützte Testtypen

Test Workflows unterstützen mehrere Testtypen innerhalb eines einzelnen Ablaufs — unabhängig oder kombiniert:

  • Web-Testing — browserbasierte UI-Automatisierung
  • Mobile Testing — iOS- und Android-App-Tests
  • API-Testing — direkte HTTP-Request-Validierung

Dies ermöglicht End-to-End-Szenarien wie: Mobile Aktion → API-Validierung → Web-Überprüfung.

Erste Schritte

Ihren ersten Test Workflow in 5 Minuten erstellen

Dieses Schnell-Tutorial führt Sie durch das Erstellen, Verfeinern und Debuggen eines einfachen Test Workflows in Autemos. Am Ende werden Sie einen funktionierenden, testbereiten Workflow haben.

1

Einen Test Workflow öffnen

Im Demo-Projekt finden Sie Beispieltests für Mobile, Web und einen kombinierten Ablauf. Nach der Auswahl eines Tests sehen Sie die Workflow-Canvas, auf der jeder Schritt als Node dargestellt ist. Aufgezeichnete Workflows umfassen typischerweise den App-Start, grundlegende Benutzerinteraktionen und Navigationsschritte.

2

Die Workflow-Struktur prüfen

Scannen Sie den Workflow von oben nach unten. Achten Sie auf eine klare Schrittabfolge (z. B. Login → Navigate → Aktion), fehlende Validierungen und fest codierte oder unklare Werte. In dieser Phase sind die meisten Workflows funktionsfähig, aber noch nicht robust oder wiederverwendbar.

3

Eine Validierung hinzufügen

Fügen Sie nach einer wichtigen Aktion einen Assert- oder Soft Verify-Node hinzu, um zu überprüfen, ob ein Bildschirm sichtbar ist, ein Wert korrekt ist oder ein Element vorhanden ist.

💡Verwenden Sie Soft Verify, wenn der Test auch bei einem fehlgeschlagenen Check fortgesetzt werden soll.
4

Testdaten einführen

Ersetzen Sie statische Werte durch dynamische Daten mithilfe des Test Data Easy-Nodes. Fügen Sie den Node direkt nach dem Startnode am Anfang des Workflows ein. Dadurch kann Ihr Workflow mit verschiedenen Datensätzen ausgeführt und szenarioübergreifend wiederverwendet werden.

5

Aufräumen und Strukturieren

Benennen Sie Nodes zur besseren Übersicht um (z. B. "Click Button" → "Click Login"), gruppieren Sie logische Schritte gedanklich (Login, Navigation, Aktion) und entfernen Sie unnötige Schritte. Ein übersichtlicher Workflow ist einfacher zu debuggen und zu pflegen.

6

Den Workflow debuggen

Wechseln Sie in den Debug-Modus. Setzen Sie einen Breakpoint bei einem kritischen Schritt, führen Sie den Workflow aus, arbeiten Sie Schritt für Schritt und beobachten Sie das Verhalten in der Live-Ansicht. Nutzen Sie das Execution Log, um Timing, Erfolg/Fehler und Fehler zu überprüfen. Beheben Sie Probleme sofort.

7

Testbereitschaft bestätigen

Ihr Workflow ist bereit, wenn: alle Schritte erfolgreich ausgeführt werden, Validierungen vorhanden sind, Testdaten korrekt konfiguriert sind und beim Debuggen keine blockierenden Fehler auftreten. Der Workflow kann nun zuverlässig in automatisierten Runs über den Scheduler ausgeführt werden.

Einen Workflow debuggen

Autemos bietet leistungsstarke Debugging-Funktionen, um sicherzustellen, dass Workflows wie erwartet funktionieren. Wechseln Sie direkt von der Workflow-Canvas zwischen Run- und Debug-Modus.

Zwischen Run- und Debug-Modus über die Canvas-Toolbar umschalten.

Debug-Modus

Beim Ausführen eines Workflows im Debug-Modus können Sie:

  • Breakpoints bei kritischen Schritten setzen
  • Schritte einzeln mit der Step-Schaltfläche ausführen
  • Die Ausführung jederzeit fortsetzen oder anhalten
Debug-Steuerelemente — Resume, Step, Stop und Paused-Zustand.
Breakpoints setzen, um die Workflow-Ausführung bei einem bestimmten Schritt anzuhalten und zu untersuchen.

Execution Log

Das Execution Log liefert schrittweise Statusaktualisierungen, Ausführungszeiten und detaillierte Fehlerinformationen. Verwenden Sie es, um genau zu ermitteln, welcher Schritt fehlgeschlagen ist und warum.

Live-Ausführungsansicht

Live Device View — Echtzeit-Interaktion mit der Anwendung während der Ausführung beobachten.

Für UI-basierte Tests (Web oder Mobile) zeigt eine Live-Ansicht die Echtzeit-Interaktion mit der Anwendung, eine visuelle Bestätigung jedes Schritts und die Möglichkeit, die Ansicht in einem separaten Tab zu öffnen. Dies erleichtert die schnelle Identifizierung und Behebung von Problemen.

Error Handling & Soft Verify

Workflows unterstützen flexible Fehlerbehandlungsstrategien.

Standardverhalten

Standardmässig stoppt ein Workflow die Ausführung, wenn ein Schritt fehlschlägt. Dies ist die sicherste Option und stellt sicher, dass Probleme sofort sichtbar werden.

Soft Verify

Bei Verwendung von Soft Verify werden Fehler protokolliert und die Ausführung fortgesetzt. Dies ist nützlich, wenn mehrere Validierungen ausgeführt werden sollen und Sie ein vollständiges Testergebnis anstelle eines vorzeitigen Abbruchs wünschen.

Ein fehlgeschlagener Schritt zeigt die Fehlerdetails inline an — XPath- oder Selector-Probleme werden direkt am Node angezeigt.

Wann welchen Ansatz verwenden

Standard (Bei Fehler stoppen)

Verwenden Sie dies, wenn ein Schrittfehler alle nachfolgenden Schritte sinnlos macht. Wenn z. B. der Login fehlschlägt, macht eine Fortsetzung keinen Sinn.

Soft Verify (Fortsetzen)

Verwenden Sie dies, wenn Sie alle Validierungsfehler in einem einzigen Run sammeln möchten, z. B. bei Formularfeldvalidierungen oder UI-Zustandsüberprüfungen.

Einen Workflow für die Ausführung vorbereiten

Bevor ein Workflow automatisch im Headless-Modus ausgeführt werden kann (z. B. in einem Scheduler), muss er testbereit sein. Ein Test gilt als bereit, wenn:

  • Alle Schritte erfolgreich ausgeführt werden
  • Datenabhängigkeiten aufgelöst sind
  • Keine blockierenden Fehler mehr vorhanden sind

Self-Healing

Autemos bietet Self-Healing-Funktionen für die Element-Identifikation. Wenn sich ein UI-Element zwischen Testläufen ändert — z. B. wenn eine CSS-Klasse, ID oder ein Attribut geändert wird — kann das System versuchen, sich automatisch zu erholen.

Self-Healing — automatische Wiederherstellung bei UI-Änderungen.

Geringere Instabilität

Tests funktionieren auch bei kleineren UI-Änderungen ohne manuellen Eingriff weiterhin.

Geringerer Wartungsaufwand

Self-Healing reduziert den Zeitaufwand für die Aktualisierung von Selectors nach Anwendungsupdates.

💡Self-Healing funktioniert am besten, wenn Elemente im Page Object Repository mit mehreren Selector-Strategien registriert sind. Je mehr Fallback-Strategien verfügbar sind, desto höher ist die Wiederherstellungsrate.

  • Vorbereitung von Workflows für lokales Debugging oder automatisierte Ausführung

Time Gap

Control Flow

Der Time Gap Node teilt einen Test Workflow in asynchrone Teile auf und setzt die Ausführung zu einem späteren Zeitpunkt fort.

Im Gegensatz zum normalen Wait Node bleibt die Workflow-Ausführung beim Time Gap Node nicht aktiv. Stattdessen wird der aktuelle Workflow-Teil abgeschlossen, persistiert und der nächste Teil separat eingeplant. Dadurch werden langlaufende und asynchrone Automatisierungsszenarien ermöglicht.

💡Time Gap ist essenziell für Enterprise-Workflows, welche verzögerte Fortsetzungen, asynchrone Prozesse oder geplante Folgevalidierungen benötigen.

Wann verwenden

Verwende den Time Gap Node wenn:

  • mehrere Minuten, Stunden oder Tage gewartet werden müssen
  • asynchrone Backend-Prozesse verarbeitet werden
  • auf externe Systeme gewartet werden muss
  • mehrteilige Workflows erstellt werden
  • verzögerte Business-Events validiert werden
  • zukünftige Workflow-Fortsetzungen geplant werden
  • Retry- oder Follow-up-Workflows benötigt werden

Typische Beispiele: Sendungsverfolgung nach Versand · Warten auf Zahlungsbestätigung · Verzögerte E-Mail-Verifizierung · Overnight-Processing · Langlaufende Business-Workflows.

💡Time Gap erstellt eine echte asynchrone Workflow-Grenze.

Definiert den minimalen Konfidenzwert, der für automatisches Healing erforderlich ist. Bereich: 0.0–1.0. Höhere Werte sind sicherer und konservativer; niedrigere Werte ermöglichen aggressiveres automatisches Healing.

Definiert den minimalen Konfidenzwert für die Generierung von Healing-Vorschlägen. Dieser Schwellenwert ist typischerweise niedriger als der Auto-Heal-Threshold, damit auch Vorschläge mit niedrigerer Konfidenz für die manuelle Überprüfung angezeigt werden.

Begrenzt die maximale Anzahl von Healing-Operationen, die während einer einzelnen Ausführung erlaubt sind. Verhindert instabile endlose Healing-Schleifen und schützt die Gesamtausführungsqualität.

Der Recorder ist der schnellste Weg, automatisierte Tests in Autemos zu erstellen. Statt Workflows manuell Schritt für Schritt aufzubauen, können Benutzer einfach mit der Anwendung interagieren, während Autemos sämtliche Aktionen automatisch aufzeichnet und in wiederverwendbare Test Workflows umwandelt.

Erste Schritte

On-Premise Stack

Autemos lässt sich vollständig im eigenen Haus betreiben — auf einem einzelnen Notebook, auf einem Server im Firmennetz oder in einer streng abgeschotteten Umgebung ohne Internetzugang. Der komplette Stack läuft als Docker-Compose-Verbund: Anwendung, Datenbank, Browser-Grid und optional ein lokales Sprachmodell. Es besteht keine Abhängigkeit zu externen Diensten.

Betriebsmodelle

Einzelplatz

Der gesamte Stack läuft auf einem Notebook. Zugriff über localhost. Ideal für Evaluierung, Schulungen und Demos.

Server im Firmennetz

Der Stack läuft zentral auf einem Server, mehrere Anwender greifen per Browser zu. Erfordert das Anpassen von zwei URLs in der Konfiguration.

Air-Gap / Offline

Installation ohne jeden Internetzugang aus einem vorbereiteten Bundle. Alle Container-Images und das LLM-Modell sind darin bereits enthalten.

Hybrid-LLM

Der Stack läuft lokal, die KI-Funktionen nutzen einen bereits vorhandenen LLM-Dienst — lokal, im Netz oder als Cloud-Endpoint.

Lieferumfang

Die Auslieferung erfolgt als Ordner autemos-offline/, der alles Nötige mitbringt:

  • Alle Container-Images als Archivdateien im Unterordner images/
  • Die fertige docker-compose.yml sowie die Konfigurationsdatei .env mit bereits generierten Passwörtern
  • Das lokale Sprachmodell im Unterordner ollama-data/
  • Hilfsskripte zum Laden der Images und zum Vorwärmen des Modells — jeweils für Linux/macOS und für Windows
💡Da alle Images mitgeliefert werden, benötigt das Zielsystem zu keinem Zeitpunkt eine Verbindung zu einer Container-Registry oder zum Internet.

Architektur

Der Stack besteht aus mehreren Containern, die untereinander über ein internes Docker-Netzwerk kommunizieren. Nach aussen sind nur wenige Ports veröffentlicht.

Komponenten

KomponenteAufgabePort (Host)

BackendZentrale Anwendungslogik: Projekte, Workflows, Testläufe, Einstellungen, LLM-Anbindung.intern

Interne Namen und externe Adressen

Innerhalb des Compose-Verbunds erreichen sich die Container über ihren Dienstnamen, nicht über localhost. Das ist die häufigste Fehlerquelle bei der Konfiguration.

BlickwinkelAdresse für Ollama
Aus einem Container heraus (z. B. Backend)http://ollama:11434
Vom Host-System / aus dem Browserhttp://localhost:11434
⚠️localhost bedeutet im Container etwas anderes. Trägt man in einer Einstellung, die vom Backend ausgewertet wird, localhost ein, zeigt das auf den Backend-Container selbst — nicht auf den Host und nicht auf einen anderen Dienst.

Skalierung des Grids

Die beiden mitgelieferten Chrome-Nodes laufen dauerhaft und unabhängig. Zusätzlich kann Autemos bei Bedarf weitere Nodes dynamisch starten; dafür wird der Docker-Socket verwendet. Steht dieser nicht zur Verfügung, bleiben die statischen Nodes davon unberührt und die Testausführung funktioniert weiterhin.

💡Der Status des Grids inklusive aller Nodes und laufender Sessions ist in der Anwendung unter Grid Dashboard einsehbar.
Installation

Systemvoraussetzungen

Der Stack stellt keine besonderen Anforderungen an das Betriebssystem — entscheidend sind Docker, die Prozessorarchitektur und ausreichend Arbeitsspeicher für das gewünschte Sprachmodell.

Basis

AnforderungDetails
DockerDocker Desktop oder Docker Engine, installiert und gestartet — inklusive Docker Compose v2.
Architekturx86-64 / amd64. Die Images sind für amd64 gebaut.
SpeicherplatzRund 30 GB frei für die geladenen Images und die Anwendungsdaten.
ArbeitsspeicherAbhängig vom Sprachmodell — siehe unten. Ohne lokales LLM deutlich weniger.
⚠️Apple Silicon wird nicht unterstützt. Der Stack läuft ausschliesslich auf amd64-Systemen, nicht auf arm64-Maschinen wie Macs mit M-Prozessor.

Arbeitsspeicher für das lokale Sprachmodell

Wird das mitgelieferte Modell qwen3-coder:30b mit 32k Kontext auf der CPU betrieben, sind rund 24 GB RAM oder mehr erforderlich. Eine GPU wird empfohlen, ist aber nicht zwingend.

💡Kleinere Modelle wie qwen2.5-coder:7b sind spürbar schneller und genügsamer. Für den AI-Recorder sind sie allerdings zu schwach — dort liefert erst ein grösseres Modell brauchbare Ergebnisse.

Alternativ lässt sich das lokale Modell ganz weglassen und stattdessen ein bereits vorhandener LLM-Dienst anbinden. Der RAM-Bedarf des Stacks sinkt dann erheblich — siehe OpenAI-kompatible Schnittstelle.

Installation

Die Installation besteht aus drei Schritten: Bundle auf das Zielsystem bringen, Images in Docker laden, Stack starten.

1

Bundle auf das Zielsystem kopieren

Den kompletten Ordner autemos-offline/ per USB-Datenträger oder Netzwerkfreigabe auf den Zielrechner übertragen, anschliessend eine Konsole in diesem Ordner öffnen.

cd autemos-offline
2

Container-Images laden

Das mitgelieferte Skript importiert alle Archivdateien aus images/ in die lokale Docker-Installation.

# Linux / macOS / Git Bash
./load-images.sh

# Windows PowerShell
.\load-images.ps1

Alternativ lassen sich die Archive einzeln laden: docker load -i images/<datei>.tar für jede Datei im Ordner.

3

Stack starten

Die danebenliegende Datei .env wird automatisch eingelesen. Beim ersten Start dauert es einen Moment, bis alle Dienste bereit sind — es laufen Datenbankmigrationen und Healthchecks.

docker compose up -d

Soll der Stack auf einem Server statt lokal laufen, müssen vorher zwei URLs angepasst werden — siehe Zugriff & URLs.

4

Status prüfen

Alle Dienste sollten den Status running bzw. healthy erreichen.

docker compose ps
docker compose logs -f

LLM-Anbindung

OpenAI-kompatible Schnittstelle

Autemos spricht Sprachmodelle nicht über proprietäre Protokolle an, sondern über eine OpenAI-kompatible Schnittstelle. Anbindbar ist damit jeder Dienst, der dieses verbreitete API-Schema bedient — unabhängig davon, ob er im Stack mitläuft, im Firmennetz steht oder als Cloud-Endpoint bereitgestellt wird.

Mögliche Gegenstellen

Ollama im Stack

Der mitgelieferte Container. Keine weitere Infrastruktur nötig, keine Daten verlassen das System.

Ollama als eigener Dienst

Eine bereits vorhandene Ollama-Installation auf dem Host oder auf einem anderen Rechner im Netz.

Firmeninternes LLM-Gateway

Ein zentral betriebener Dienst mit OpenAI-kompatiblem Endpoint, an dem sich mehrere Anwendungen bedienen.

Cloud-Endpoint

Zum Beispiel Azure AI Foundry oder ein vergleichbarer Anbieter. Sinnvoll, wenn keine lokale Rechenleistung bereitsteht.

Welche URL gehört ins Feld „LLM Server URL"?

Die einzutragende Adresse hängt davon ab, wo der Dienst läuft — und zwar aus Sicht des Backends, das die Anfragen stellt.

LLM-Anbindung

Einrichtung in der UI

Das mitgelieferte Modell liegt bereits im Ordner ollama-data/ und muss nicht heruntergeladen werden. Die Verbindung wird einmalig in der Oberfläche hergestellt.

1

Einstellungen öffnen

In der Anwendung zu Global Settings → LLM Integration wechseln.

2

LLM global aktivieren

Die Option „Enable LLM for field generation globally" einschalten.

3

Provider wählen

Als Provider Ollama / OpenAI-compatible auswählen.

4

Server-URL eintragen

Bei Betrieb im mitgelieferten Stack: http://ollama:11434. Für abweichende Betriebsarten siehe OpenAI-kompatible Schnittstelle.

5

Modell auswählen

Auf „Load models" klicken und aus der Liste qwen3-coder:30b wählen. Den API-Key leer lassen.

6

Speichern und prüfen

Mit Save übernehmen, anschliessend Test Connection ausführen. Die Rückmeldung sollte positiv ausfallen.

💡Vor dem ersten produktiven Aufruf sollte das Modell einmal vorgewärmt werden — siehe Modell vorwärmen. Andernfalls kann der erste Aufruf in eine Zeitüberschreitung laufen.
LLM-Anbindung

Modell vorwärmen

Beim ersten Aufruf lädt Ollama das Modell von der Festplatte in den Arbeitsspeicher. Auf der CPU kann das bei einem grossen Modell wie qwen3-coder:30b mehrere Minuten dauern. Damit der erste echte Aufruf aus der Anwendung nicht in eine Zeitüberschreitung läuft, wird das Modell einmal gezielt vorgewärmt.

# Linux / macOS / Git Bash
./warmup-ollama.sh

# Windows PowerShell
.\warmup-ollama.ps1

# Falls die Ausführungsrichtlinie das Skript blockiert:
powershell -ExecutionPolicy Bypass -File .\warmup-ollama.ps1

Das Skript wartet, bis das Modell vollständig geladen ist, gibt die benötigte Dauer aus und prüft abschliessend, dass das Modell tatsächlich im Speicher liegt. Ein zweiter Lauf sollte nur noch wenige Sekunden benötigen — dann ist das Modell warm.

Warum das Modell geladen bleibt

Ohne Gegenmassnahme entlädt Ollama ein Modell nach etwa fünf Minuten ohne Anfragen wieder aus dem Speicher; der nächste Aufruf wäre erneut kalt. Im mitgelieferten Stack ist deshalb OLLAMA_KEEP_ALIVE=-1 gesetzt — das Modell bleibt nach dem ersten Laden dauerhaft geladen.

💡Der Wert lässt sich in der .env überschreiben, etwa auf OLLAMA_KEEP_ALIVE=24h, wenn der Speicher nach längerer Inaktivität wieder freigegeben werden soll.
Betrieb

Konfiguration & Secrets

Sämtliche Betriebsparameter des Stacks stehen in der Datei .env neben der docker-compose.yml. Sie wird beim Start automatisch eingelesen. Nach einer Änderung genügt ein erneutes docker compose up -d.

Zugangsdaten

Die ausgelieferte .env enthält bereits zufällig generierte Werte für die folgenden Einträge:

EintragBedeutung
POSTGRES_PASSWORDPasswort der Datenbank
JWT_SECRETSchlüssel zur Signatur der Anmelde-Tokens
BACKEND_SERVICE_PASSPasswort für die interne Dienstkommunikation
⚠️Für einen produktiven Einsatz sollten diese Werte durch eigene ersetzt und der Stack anschliessend neu gestartet werden. Die .env ist entsprechend zu schützen — sie enthält alle Zugangsdaten im Klartext.

Ports

Sind Ports auf dem Zielsystem bereits belegt, lassen sich die veröffentlichten Ports in der .env anpassen — etwa FRONTEND_PORT oder GRID_HUB_PORT. Danach den Stack neu starten.

💡Wird FRONTEND_PORT geändert, müssen FRONTEND_BASE_URL und WORKER_EXTERNAL_URL passend nachgezogen werden.

GPU-Nutzung

Standardmässig rechnet Ollama auf der CPU. Steht auf dem Zielsystem eine NVIDIA-GPU zur Verfügung, lässt sich die Inferenz deutlich beschleunigen. Dazu wird das NVIDIA Container Toolkit auf dem Host installiert und beim Dienst ollama in der docker-compose.yml eine GPU-Reservierung ergänzt.

Zeitlimit für LLM-Anfragen

Das Zeitlimit für Anfragen an das Sprachmodell steht standardmässig auf 180 Sekunden — ein Wert, der auch bei CPU-Betrieb tragfähig ist. Benötigt ein grosses Modell auch im warmen Zustand länger, lässt sich der Wert unter Global Settings → LLM Integration erhöhen.

Anderes Sprachmodell

Welches Modell im Bundle enthalten ist, wird bei dessen Erstellung festgelegt und lässt sich auf einem Offline-System nicht nachträglich austauschen — dafür wäre ein Download erforderlich. Wird ein kleineres oder grösseres Modell benötigt, ist ein entsprechend erstelltes Bundle anzufordern.

💡Besteht auf dem Zielsystem doch eine Netzwerkverbindung zu einem LLM-Dienst, lässt sich das mitgelieferte Modell umgehen und stattdessen ein externer Endpoint anbinden — siehe OpenAI-kompatible Schnittstelle.

Betrieb

Der laufende Betrieb erfolgt vollständig über Docker Compose aus dem Bundle-Ordner heraus.

BefehlWirkung
docker compose up -dStack starten bzw. nach Konfigurationsänderungen neu anwenden
docker compose downStack stoppen — alle Daten bleiben erhalten
docker compose psStatus aller Dienste anzeigen
docker compose logs -fLogs fortlaufend mitlesen
docker compose down -vAlles löschen, einschliesslich des Datenbank-Volumes
⚠️docker compose down -v entfernt das Datenbank-Volume und damit sämtliche Projekte, Workflows und Testergebnisse unwiderruflich. Zum normalen Stoppen ist docker compose down ohne -v zu verwenden.

Datenhaltung

Alle Anwendungsdaten liegen in einem Docker-Volume und überstehen Stoppen, Starten und Neustarts des Hosts. Ein Backup des Stacks bedeutet daher im Wesentlichen ein Backup dieses Volumes zuzüglich der Datei .env.
