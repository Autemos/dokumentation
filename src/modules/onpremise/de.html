Erste Schritte

On-Premise Stack

Autemos lässt sich vollständig im eigenen Haus betreiben — auf einem einzelnen Notebook, auf einem Server im Firmennetz oder in einer streng abgeschotteten Umgebung ohne Internetzugang. Der komplette Stack läuft als Docker-Compose-Verbund: Anwendung, Datenbank, Browser-Grid und optional ein lokales Sprachmodell. Es besteht keine Abhängigkeit zu externen Diensten.

Betriebsmodelle

Einzelplatz

Der gesamte Stack läuft auf einem Notebook. Zugriff über localhost. Ideal für Evaluierung, Schulungen und Demos.

Server im Firmennetz

Der Stack läuft zentral auf einem Server, mehrere Anwender greifen per Browser zu. Erfordert das Anpassen von zwei URLs in der Konfiguration.

Air-Gap / Offline

Installation ohne jeden Internetzugang aus einem vorbereiteten Bundle. Alle Container-Images und das LLM-Modell sind darin bereits enthalten.

Hybrid-LLM

Der Stack läuft lokal, die KI-Funktionen nutzen einen bereits vorhandenen LLM-Dienst — lokal, im Netz oder als Cloud-Endpoint.

Lieferumfang

Die Auslieferung erfolgt als Ordner autemos-offline/, der alles Nötige mitbringt:

  • Alle Container-Images als Archivdateien im Unterordner images/
  • Die fertige docker-compose.yml sowie die Konfigurationsdatei .env mit bereits generierten Passwörtern
  • Das lokale Sprachmodell im Unterordner ollama-data/
  • Hilfsskripte zum Laden der Images und zum Vorwärmen des Modells — jeweils für Linux/macOS und für Windows
💡Da alle Images mitgeliefert werden, benötigt das Zielsystem zu keinem Zeitpunkt eine Verbindung zu einer Container-Registry oder zum Internet.
Erste Schritte

Architektur

Der Stack besteht aus mehreren Containern, die untereinander über ein internes Docker-Netzwerk kommunizieren. Nach aussen sind nur wenige Ports veröffentlicht.

Komponenten

KomponenteAufgabePort (Host)
FrontendWeboberfläche von Autemos. Dient zugleich als Einstiegspunkt und leitet Anfragen an Backend und Worker weiter.3000
BackendZentrale Anwendungslogik: Projekte, Workflows, Testläufe, Einstellungen, LLM-Anbindung.intern
Java-WorkerFührt die Testworkflows aus und steuert die Browser im Grid.über /worker
PostgreSQLDatenbank für alle Projekt-, Test- und Konfigurationsdaten. Liegt in einem Docker-Volume.intern
Selenium Grid HubVerteilt Testsitzungen auf die verfügbaren Browser-Nodes.4444
Chrome-NodesZwei statische Browser-Nodes für die Testausführung.über den Hub
OllamaLokaler LLM-Dienst für KI-Funktionen wie Feldgenerierung, AI-Recorder und Auto-Healing.11434

Interne Namen und externe Adressen

Innerhalb des Compose-Verbunds erreichen sich die Container über ihren Dienstnamen, nicht über localhost. Das ist die häufigste Fehlerquelle bei der Konfiguration.

BlickwinkelAdresse für Ollama
Aus einem Container heraus (z. B. Backend)http://ollama:11434
Vom Host-System / aus dem Browserhttp://localhost:11434
⚠️localhost bedeutet im Container etwas anderes. Trägt man in einer Einstellung, die vom Backend ausgewertet wird, localhost ein, zeigt das auf den Backend-Container selbst — nicht auf den Host und nicht auf einen anderen Dienst.

Skalierung des Grids

Die beiden mitgelieferten Chrome-Nodes laufen dauerhaft und unabhängig. Zusätzlich kann Autemos bei Bedarf weitere Nodes dynamisch starten; dafür wird der Docker-Socket verwendet. Steht dieser nicht zur Verfügung, bleiben die statischen Nodes davon unberührt und die Testausführung funktioniert weiterhin.

💡Der Status des Grids inklusive aller Nodes und laufender Sessions ist in der Anwendung unter Grid Dashboard einsehbar.
Installation

Systemvoraussetzungen

Der Stack stellt keine besonderen Anforderungen an das Betriebssystem — entscheidend sind Docker, die Prozessorarchitektur und ausreichend Arbeitsspeicher für das gewünschte Sprachmodell.

Basis

AnforderungDetails
DockerDocker Desktop oder Docker Engine, installiert und gestartet — inklusive Docker Compose v2.
Architekturx86-64 / amd64. Die Images sind für amd64 gebaut.
SpeicherplatzRund 30 GB frei für die geladenen Images und die Anwendungsdaten.
ArbeitsspeicherAbhängig vom Sprachmodell — siehe unten. Ohne lokales LLM deutlich weniger.
⚠️Apple Silicon wird nicht unterstützt. Der Stack läuft ausschliesslich auf amd64-Systemen, nicht auf arm64-Maschinen wie Macs mit M-Prozessor.

Arbeitsspeicher für das lokale Sprachmodell

Wird das mitgelieferte Modell qwen3-coder:30b mit 32k Kontext auf der CPU betrieben, sind rund 24 GB RAM oder mehr erforderlich. Eine GPU wird empfohlen, ist aber nicht zwingend.

💡Kleinere Modelle wie qwen2.5-coder:7b sind spürbar schneller und genügsamer. Für den AI-Recorder sind sie allerdings zu schwach — dort liefert erst ein grösseres Modell brauchbare Ergebnisse.

Alternativ lässt sich das lokale Modell ganz weglassen und stattdessen ein bereits vorhandener LLM-Dienst anbinden. Der RAM-Bedarf des Stacks sinkt dann erheblich — siehe OpenAI-kompatible Schnittstelle.

Installation

Installation

Die Installation besteht aus drei Schritten: Bundle auf das Zielsystem bringen, Images in Docker laden, Stack starten.

1

Bundle auf das Zielsystem kopieren

Den kompletten Ordner autemos-offline/ per USB-Datenträger oder Netzwerkfreigabe auf den Zielrechner übertragen, anschliessend eine Konsole in diesem Ordner öffnen.

cd autemos-offline
2

Container-Images laden

Das mitgelieferte Skript importiert alle Archivdateien aus images/ in die lokale Docker-Installation.

# Linux / macOS / Git Bash
./load-images.sh

# Windows PowerShell
.\load-images.ps1

Alternativ lassen sich die Archive einzeln laden: docker load -i images/<datei>.tar für jede Datei im Ordner.

3

Stack starten

Die danebenliegende Datei .env wird automatisch eingelesen. Beim ersten Start dauert es einen Moment, bis alle Dienste bereit sind — es laufen Datenbankmigrationen und Healthchecks.

docker compose up -d

Soll der Stack auf einem Server statt lokal laufen, müssen vorher zwei URLs angepasst werden — siehe Zugriff & URLs.

4

Status prüfen

Alle Dienste sollten den Status running bzw. healthy erreichen.

docker compose ps
docker compose logs -f

Betrieb auf einem Server

Läuft der Stack nicht lokal, sondern auf einem Server, auf den andere Rechner per Browser zugreifen, müssen in der Datei .env vor dem ersten Start zwei Einträge von localhost auf den Servernamen oder die Server-IP umgestellt werden:

LLM-Anbindung

OpenAI-kompatible Schnittstelle

Autemos spricht Sprachmodelle nicht über proprietäre Protokolle an, sondern über eine OpenAI-kompatible Schnittstelle. Anbindbar ist damit jeder Dienst, der dieses verbreitete API-Schema bedient — unabhängig davon, ob er im Stack mitläuft, im Firmennetz steht oder als Cloud-Endpoint bereitgestellt wird.

Mögliche Gegenstellen

Ollama im Stack

Der mitgelieferte Container. Keine weitere Infrastruktur nötig, keine Daten verlassen das System.

Ollama als eigener Dienst

Eine bereits vorhandene Ollama-Installation auf dem Host oder auf einem anderen Rechner im Netz.

Firmeninternes LLM-Gateway

Ein zentral betriebener Dienst mit OpenAI-kompatiblem Endpoint, an dem sich mehrere Anwendungen bedienen.

Cloud-Endpoint

Zum Beispiel Azure AI Foundry oder ein vergleichbarer Anbieter. Sinnvoll, wenn keine lokale Rechenleistung bereitsteht.

Welche URL gehört ins Feld „LLM Server URL"?

Die einzutragende Adresse hängt davon ab, wo der Dienst läuft — und zwar aus Sicht des Backends, das die Anfragen stellt.

BetriebsartLLM Server URLHinweis
Ollama im mitgelieferten Stackhttp://ollama:11434Interner Dienstname des Containers
Ollama als lokaler Dienst, ohne Container-Trennunghttp://localhost:11434Nur korrekt, wenn Dienst und Backend denselben Netzwerkkontext teilen
Ollama auf einem anderen Rechnerhttp://<hostname-oder-ip>:11434Port muss von aussen erreichbar sein
Cloud- oder Gateway-EndpointVollständige Basis-URL des Anbieters, z. B. https://api.openai.com/v1Adresse und Pfad exakt so übernehmen, wie vom Anbieter dokumentiert
⚠️Läuft Ollama im Compose-Stack, ist http://localhost:11434 an dieser Stelle falsch. Aus Sicht des Backend-Containers verweist localhost auf den Container selbst. Korrekt ist hier ausschliesslich der Dienstname http://ollama:11434.

LLM-Anbindung

Einrichtung in der UI

Das mitgelieferte Modell liegt bereits im Ordner ollama-data/ und muss nicht heruntergeladen werden. Die Verbindung wird einmalig in der Oberfläche hergestellt.

1

Einstellungen öffnen

In der Anwendung zu Global Settings → LLM Integration wechseln.

2

LLM global aktivieren

Die Option „Enable LLM for field generation globally" einschalten.

3

Provider wählen

Als Provider Ollama / OpenAI-compatible auswählen.

4

Server-URL eintragen

Bei Betrieb im mitgelieferten Stack: http://ollama:11434. Für abweichende Betriebsarten siehe OpenAI-kompatible Schnittstelle.

5

Modell auswählen

Auf „Load models" klicken und aus der Liste qwen3-coder:30b wählen. Den API-Key leer lassen.

6

Speichern und prüfen

Mit Save übernehmen, anschliessend Test Connection ausführen. Die Rückmeldung sollte positiv ausfallen.

💡Vor dem ersten produktiven Aufruf sollte das Modell einmal vorgewärmt werden — siehe Modell vorwärmen. Andernfalls kann der erste Aufruf in eine Zeitüberschreitung laufen.
LLM-Anbindung

Modell vorwärmen

Beim ersten Aufruf lädt Ollama das Modell von der Festplatte in den Arbeitsspeicher. Auf der CPU kann das bei einem grossen Modell wie qwen3-coder:30b mehrere Minuten dauern. Damit der erste echte Aufruf aus der Anwendung nicht in eine Zeitüberschreitung läuft, wird das Modell einmal gezielt vorgewärmt.

# Linux / macOS / Git Bash
./warmup-ollama.sh

# Windows PowerShell
.\warmup-ollama.ps1

# Falls die Ausführungsrichtlinie das Skript blockiert:
powershell -ExecutionPolicy Bypass -File .\warmup-ollama.ps1

Das Skript wartet, bis das Modell vollständig geladen ist, gibt die benötigte Dauer aus und prüft abschliessend, dass das Modell tatsächlich im Speicher liegt. Ein zweiter Lauf sollte nur noch wenige Sekunden benötigen — dann ist das Modell warm.

Warum das Modell geladen bleibt

Ohne Gegenmassnahme entlädt Ollama ein Modell nach etwa fünf Minuten ohne Anfragen wieder aus dem Speicher; der nächste Aufruf wäre erneut kalt. Im mitgelieferten Stack ist deshalb OLLAMA_KEEP_ALIVE=-1 gesetzt — das Modell bleibt nach dem ersten Laden dauerhaft geladen.

💡Der Wert lässt sich in der .env überschreiben, etwa auf OLLAMA_KEEP_ALIVE=24h, wenn der Speicher nach längerer Inaktivität wieder freigegeben werden soll.
Betrieb

Konfiguration & Secrets

Sämtliche Betriebsparameter des Stacks stehen in der Datei .env neben der docker-compose.yml. Sie wird beim Start automatisch eingelesen. Nach einer Änderung genügt ein erneutes docker compose up -d.

Zugangsdaten

Die ausgelieferte .env enthält bereits zufällig generierte Werte für die folgenden Einträge:

EintragBedeutung
POSTGRES_PASSWORDPasswort der Datenbank
JWT_SECRETSchlüssel zur Signatur der Anmelde-Tokens
BACKEND_SERVICE_PASSPasswort für die interne Dienstkommunikation
⚠️Für einen produktiven Einsatz sollten diese Werte durch eigene ersetzt und der Stack anschliessend neu gestartet werden. Die .env ist entsprechend zu schützen — sie enthält alle Zugangsdaten im Klartext.

Ports

Sind Ports auf dem Zielsystem bereits belegt, lassen sich die veröffentlichten Ports in der .env anpassen — etwa FRONTEND_PORT oder GRID_HUB_PORT. Danach den Stack neu starten.

💡Wird FRONTEND_PORT geändert, müssen FRONTEND_BASE_URL und WORKER_EXTERNAL_URL passend nachgezogen werden.

GPU-Nutzung

Standardmässig rechnet Ollama auf der CPU. Steht auf dem Zielsystem eine NVIDIA-GPU zur Verfügung, lässt sich die Inferenz deutlich beschleunigen. Dazu wird das NVIDIA Container Toolkit auf dem Host installiert und beim Dienst ollama in der docker-compose.yml eine GPU-Reservierung ergänzt.

Zeitlimit für LLM-Anfragen

Das Zeitlimit für Anfragen an das Sprachmodell steht standardmässig auf 180 Sekunden — ein Wert, der auch bei CPU-Betrieb tragfähig ist. Benötigt ein grosses Modell auch im warmen Zustand länger, lässt sich der Wert unter Global Settings → LLM Integration erhöhen.

Anderes Sprachmodell

Welches Modell im Bundle enthalten ist, wird bei dessen Erstellung festgelegt und lässt sich auf einem Offline-System nicht nachträglich austauschen — dafür wäre ein Download erforderlich. Wird ein kleineres oder grösseres Modell benötigt, ist ein entsprechend erstelltes Bundle anzufordern.

💡Besteht auf dem Zielsystem doch eine Netzwerkverbindung zu einem LLM-Dienst, lässt sich das mitgelieferte Modell umgehen und stattdessen ein externer Endpoint anbinden — siehe OpenAI-kompatible Schnittstelle.
Betrieb

Betrieb

Der laufende Betrieb erfolgt vollständig über Docker Compose aus dem Bundle-Ordner heraus.

BefehlWirkung
docker compose up -dStack starten bzw. nach Konfigurationsänderungen neu anwenden
docker compose downStack stoppen — alle Daten bleiben erhalten
docker compose psStatus aller Dienste anzeigen
docker compose logs -fLogs fortlaufend mitlesen
docker compose down -vAlles löschen, einschliesslich des Datenbank-Volumes
⚠️docker compose down -v entfernt das Datenbank-Volume und damit sämtliche Projekte, Workflows und Testergebnisse unwiderruflich. Zum normalen Stoppen ist docker compose down ohne -v zu verwenden.

Datenhaltung

Alle Anwendungsdaten liegen in einem Docker-Volume und überstehen Stoppen, Starten und Neustarts des Hosts. Ein Backup des Stacks bedeutet daher im Wesentlichen ein Backup dieses Volumes zuzüglich der Datei .env.

Diagnose des LLM-Dienstes

Bleibt unklar, ob das Modell geladen werden konnte, geben die Logs und die Ressourcennutzung des Ollama-Containers Aufschluss:

docker logs --tail 80 stk_prod_ollama
docker stats stk_prod_ollama --no-stream

Zeigt die Speicherauslastung, dass der Container an eine Grenze stösst, reicht der Arbeitsspeicher für das gewählte Modell nicht aus.
