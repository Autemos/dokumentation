Code-Sync

Code-Sync: Zustand und Prüfung

Wurde der generierte Testcode eines Workflows per Push to Git in ein GitHub-Repository übertragen, erkennt Autemos, wenn dieser Code später im Repository von Hand geändert wird. Der Workflow wird dabei nie stillschweigend verändert: Änderungen werden angezeigt und erst nach ausdrücklicher Entscheidung übernommen. Bei unklarem Stand zeigt Autemos nie fälschlich «In sync» an.

⚠️Nur GitHub. Der Code-Sync und Push to Git unterstützen derzeit ausschliesslich GitHub. GitLab und Bitbucket sind in der Git-Verbindung deaktiviert und werden vom Server abgewiesen.

Sync-Zustand in der Workflow-Liste

Hat das Projekt eine Git-Verbindung, zeigt die Workflow-Liste (Tabelle und Kacheln) je Workflow den Sync-Zustand. Der Zustand wird nach dem Laden der Liste nachgeladen und blockiert sie nicht. Ohne Git-Verbindung erscheinen weder Spalte noch Badge noch Knopf.

ZustandBedeutung
Not syncedDer Workflow wurde noch nie ins Repository übertragen.
PR openDer Pull Request des letzten Push to Git ist noch offen. Der Workflow gilt erst nach dem Merge als «In sync».
In syncDie Testdatei im Repository stimmt mit dem zuletzt übertragenen Stand überein.
Out of syncDie Testdatei wurde im Repository geändert oder gelöscht. Mit dem Zusatz «ignored», wenn die Änderung bewusst ignoriert wurde.
Baseline acceptedDer Repository-Stand wurde als neue Basis akzeptiert, der Workflow aber nicht daraus aktualisiert.
UnknownDer Stand konnte nicht geprüft werden (z. B. GitHub nicht erreichbar, Token ungültig, Kontingent erschöpft, Push vor Einführung der Versionsverfolgung). Der Grund steht im Tooltip.

Die Prüfung vergleicht ausschliesslich die Testdateien des jeweiligen Workflows; Commits an anderen Dateien lösen kein «Out of sync» aus. Das Ergebnis wird rund 10 Minuten zwischengespeichert. Mit dem Knopf Check now in der Kopfzeile der Liste lässt sich die Prüfung sofort auslösen.

Hinweis im Workflow-Editor

Im Workflow-Editor zeigt der Indikator «Code sync» in der Werkzeugleiste den aktuellen Zustand (Symbol; Tooltip «Code sync: …» mit Zustand, Zeitpunkt der letzten Prüfung und letztem Commit). Bei einer Änderung im Repository erscheint der Hinweis There are changes in the underlying code mit Commit, Autor und Zeitpunkt sowie dem Knopf View changes. Wurde die Änderung ignoriert, bleibt der Hinweis dezenter und erscheint bei einem neuen Commit wieder in voller Form. Ist der Stand unbekannt, erscheint Code sync state unknown mit dem Grund.

Dialog «Code changes»

Der Dialog zeigt links den zuletzt synchronisierten Code und rechts den aktuellen Stand im Repository. Oben steht der Bereich Workflow changes: die erkannten Änderungen pro Workflow-Knoten (Knotenname, Parameter, alter und neuer Wert). Darunter steht der Textvergleich des Codes zwischen der zuletzt synchronisierten Version und dem aktuellen Repository-Stand, je Datei als hinzugefügt, entfernt oder geändert gekennzeichnet. Farbig markiert sind genau die Zeilen, die auch ein git diff als hinzugefügt (grün, rechts) oder entfernt (rot, links) meldet; ein neu ergänzter Knotenblock wird mit allen seinen Zeilen markiert, die Zeile davor bleibt unmarkiert. Unter dem Vergleich zeigt Changed lines (from line n) die geänderten Zeilen als Liste. Nicht übernehmbare Änderungen sind ausdrücklich gekennzeichnet und nennen den Grund; reine Kommentar- und Leerzeilenänderungen werden als unwesentlich markiert. Ein Link Supported changes öffnet in einem neuen Tab die in Autemos ausgelieferte Dokumentation der unterstützten Änderungen (Sprachen, Frameworks, Knotenarten, Einschränkungen); er benötigt keinen Zugriff auf GitHub.

Entscheidungen

KnopfWirkung
Ignore changesDer Workflow bleibt unverändert. Der Zustand bleibt «Out of sync (ignored)», bis ein neuer Commit hinzukommt.
Accept baseline onlyDer Repository-Stand wird als neue Basis übernommen, der Workflow bleibt unverändert. Der Zustand lautet «Baseline accepted», nicht «In sync».
Apply to workflowÜbernimmt die erkannten Änderungen in den Workflow. Nach einer Bestätigung («Apply code changes to workflow?») wird der Workflow aktualisiert; der Zustand wechselt auf «In sync».
Check nowPrüft das Repository sofort erneut und aktualisiert Zustand und Vorschau.
Push to GitErzeugt den Code des Workflows neu und öffnet den Pull-Request-Dialog (siehe «Push to Git im Editor»).
CloseSchliesst den Dialog, ohne etwas zu ändern.

Regeln für «Apply to workflow»

  • Der Knopf ist gesperrt (mit Begründung), solange eine Änderung nicht unterstützt ist, der Code nicht analysiert werden konnte, ein Konflikt besteht oder die Vorschau nicht verfügbar ist. Es wird dann nichts teilweise übernommen.
  • Die Übernahme ist atomar: Entweder wird alles übernommen oder nichts. Vor der Übernahme legt Autemos eine wiederherstellbare Version «Before code sync apply (commit …)» an, danach «Applied code changes from commit …». Beide sind im Versionsverlauf als Quelle «Code sync» erkennbar.
  • Wurde der Workflow in Autemos seit dem letzten Sync bearbeitet oder wird er gerade von jemand anderem bearbeitet, meldet die Vorschau einen Konflikt und überschreibt nichts. Hat sich das Repository seit dem Öffnen des Dialogs erneut geändert, lehnt Autemos die Entscheidung mit einem Hinweis zum Neuladen ab.
  • Die resultierende Workflow-Struktur wird vor dem Speichern geprüft. Knotenarten, die der Generator nicht erzeugt, bleiben im Workflow erhalten.
  • Wird eine frühere Version des Workflows wiederhergestellt, wechselt der Sync-Zustand auf «Out of sync».
  • Die Vorschau ist nur verfügbar, wenn die Testdatei von einer Autemos-Version stammt, die Knotenmarker enthält. Bei älteren Ständen erscheint «Preview not available»; ein erneuter Push to Git behebt das. Ignorieren und Basis akzeptieren bleiben möglich.
  • Vorschau darf, wer Mitglied des Projekts ist. Übernehmen und Entscheiden setzen Editor-Rechte voraus. Alle Schritte (Vorschau angesehen, übernommen, Konflikt, wiederhergestellt, Entscheidung) erscheinen in der Audit-Übersicht in der Kategorie «Code Sync».
💡Ausgeführt wird immer der Workflow in Autemos, nie der Code aus dem Repository. Ein «Out of sync»-Workflow läuft daher unverändert weiter, bis die Änderungen übernommen wurden.

Hinweis nach «Apply to workflow»: neue Knoten-IDs

Hat «Apply to workflow» neue Schritte angelegt, steht im Code im Repository noch node=new, während die neuen Knoten in Autemos bereits eine eindeutige ID tragen. Bis der Code erneut übertragen wurde, zeigt der Workflow-Editor oberhalb des Workflows einen bleibenden Hinweis: Workflow updated. New nodes have been assigned unique IDs. mit dem Satz «Please synchronize the generated code with GitHub before making further external changes.» und dem Knopf Sync code now.

  • Sync code now öffnet den Dialog «Push to Git» für diesen Workflow. Der Lauf startet erst mit Ihrem Klick auf Create Pull Request; Autemos ändert das Repository nie von selbst. Der Knopf ist gesperrt (mit Begründung), wenn der Workflow ungespeicherte Änderungen hat oder die Projektrolle keine Editor-Rechte erlaubt.
  • Der Hinweis bleibt nach dem Neuladen und für andere Benutzer stehen, auch im Zustand «In sync». Er verschwindet, sobald der Pull Request erzeugt wurde (Zustand «PR open» zeigt ihn nicht an). Eine spätere Übernahme, die nur Parameter ändert, löscht ihn nicht.
  • Der Hinweis erscheint nur, wenn mindestens ein neuer Schritt übernommen wurde; nach reinen Änderungen oder Löschungen erscheint er nicht.
  • Solange er steht, warnt der Dialog «Code changes» oberhalb von «Workflow changes»: Schritte aus einer früheren Übernahme tragen im Repository noch node=new, deshalb können sie bei weiteren externen Änderungen als hinzugefügt und zugleich entfernt erscheinen. Übernehmen bleibt möglich; synchronisieren Sie zuerst den Code.
  • Nach der Übernahme meldet ein kurzer Hinweis: «Sync the generated code with GitHub – see the notice above the workflow.»
Code-Sync

Push to Git aus dem Workflow-Editor

Aus dem Dialog «Code changes» im Workflow-Editor erzeugt der Knopf Push to Git den Code des geöffneten Workflows und einen GitHub-Pull-Request, ohne den Editor zu verlassen. Er öffnet den gleichen Push-to-Git-Dialog wie der Generate-Tab; nur der geöffnete Workflow und die von ihm verwendeten PageObjects werden übergeben.

  • Der Knopf ist gesperrt, solange der Workflow ungespeicherte Änderungen hat («Save your changes before pushing to Git») oder wenn die Projektrolle keine Editor-Rechte erlaubt («You need editor rights in this project to push to Git»).
  • Vor dem Push prüft Autemos das Repository frisch. Hat das Repository nicht übernommene externe Änderungen, ist der Stand unbekannt oder weicht die akzeptierte Basis ab, erscheint eine Warnung und Create Pull Request bleibt gesperrt, bis die Checkbox Overwrite the external changes in the repository gesetzt ist. View changes springt in den Dialog «Code changes». Externe Änderungen werden so nie unbemerkt überschrieben.
  • Bei ignorierten Änderungen oder einem noch offenen Pull Request erscheint nur ein Hinweis, der Push bleibt frei.
  • Nach Erfolg meldet ein Hinweis Pull request #n created – not merged yet; der Indikator wechselt auf «Code sync: PR open».

Offener Pull Request und fehlende Git-Verbindung

  • Offener Pull Request: Solange der Pull Request nicht gemergt ist, gibt es nichts zu vergleichen. Der Dialog «Code changes» zeigt dann eine Information mit dem Link Open pull request #n statt eines roten Fehlers und ohne Wiederholen-Knopf. Echte Ladefehler erscheinen weiterhin als Fehler mit Retry.
  • Keine Git-Verbindung: Der Editor zeigt «Code sync: not set up». Der Dialog erklärt «No Git connection is configured for this project.» und bietet den Link Set up Git connection, der direkt in die Einrichtung des Code Generation Hub führt. Push to Git ist bis dahin gesperrt («Set up a Git connection first»).
Code-Sync

Unterstützte Code-Änderungen

Der Code-Sync liest Änderungen am generierten Testcode knotengenau zurück. Jeder Workflow-Knoten steht im generierten Code zwischen den Marker-Kommentaren @autemos node=… type=… und @autemos end. Diese Marker ordnen den Code dem Knoten zu und dürfen nicht entfernt oder verändert werden. Ein neuer Schritt wird mit @autemos node=new type=… eingeleitet.

ArtBedeutungÜbernehmbar
MODIFIEDEin Parameter eines Knotens hat sich geändert (alter → neuer Wert).Ja
ADDEDEin neuer Schritt wurde im Code ergänzt.Ja, wenn die Form unterstützt wird
REMOVEDEin Schritt wurde aus dem Code entfernt. Wird der Schritt oder seine Variable noch von anderen Knoten gelesen, ist die Übernahme gesperrt.Ja
REORDEREDDie Reihenfolge der Schritte hat sich geändert.Ja
MOVEDEin Schritt liegt in einem anderen Zweig, in oder ausserhalb eines Schleifenkörpers oder auf einer anderen Ebene.Ja (Java/Playwright)

Neue Schritte

Neue Schritte (ADDED) werden für navigate und wait in allen Sprachen übernommen. Nur bei Java/Playwright kommen ifCondition, loop und callSubWorkflow sowie in der page.locator-Form click, doubleClick, hover, check, pressKey, scroll, type, select und assert hinzu. Der neue Knoten erhält den Selektor aus dem Statement. Ein neuer Schritt, der ein PageObject-Element anspricht, ist nicht übernehmbar («new steps via a page object need the element mapping»), weil Autemos das Element nicht aus dem Code zuordnen kann; verwenden Sie die page.locator("…")-Form oder legen Sie den Schritt in Autemos an.

Selektoren in PageObject-Dateien

Ändert jemand den Selektor eines Felds in einer von Autemos erzeugten PageObject-Datei, zeigt der Sync die Änderung an jedem Knoten, der dieses Feld nutzt. Apply to workflow schreibt den neuen Selektor in das PageObject-Feld in Autemos. Das gilt für Web-PageObjects mit Playwright in Java, TypeScript, Python und C#. Felder werden über Marker @autemos pageObjectField=… zugeordnet; Felder werden in Autemos angelegt, umbenannt und entfernt, nicht im Code (ein doppelter Marker oder ein verändertes Locator-Literal wird als Problem gemeldet). In TypeScript sind Felder mit Mehrplattform-Locatoren (z. B. nur Android- oder iOS-Locator) nicht synchronisierbar. Selektoränderungen direkt im Test (page.locator("…")) werden erkannt, aber nicht übernommen.

Jeder Workflow beobachtet die PageObject-Datei in seinem eigenen Zielordner. Haben Sie dasselbe PageObject aus zwei Workflows in unterschiedliche Zielordner übertragen, sind das zwei getrennte Dateien: Eine Änderung in der einen Datei zeigt nur der Workflow an, dessen Ordner sie betrifft, und eine spätere erneute Änderung desselben Felds wird mit Check now ebenfalls erkannt. Nutzen mehrere Workflows dasselbe PageObject, nennt der Grund der Änderung die anderen Workflows (also used by: …, höchstens fünf Namen, dann +n more), weil Apply to workflow den Selektor für alle diese Workflows ändert.

Strukturänderungen: Bedingungen, Schleifen, Sub-Workflows

Bedingungen, Schleifen und Sub-Workflow-Aufrufe erscheinen im generierten Java/Playwright-Code eindeutig zuordenbar (mit eigenen Markern für Zweige und Schleifenkörper). Änderungen daran zeigt die Vorschau einzeln, inklusive der betroffenen Verbindungen (Bereiche Connections und Sub-workflow references). Übernommen wird nur, was eine gültige Workflow-Struktur ergibt; sonst ist die Änderung gekennzeichnet und «Apply to workflow» gesperrt.

Änderung im CodeErgebnis

Schritte innerhalb einer Ebene umordnenREORDERED
Neuer Schritt in einem Zweig oder SchleifenkörperADDED mit Strukturpfad (z. B. «if1 › true»)
Schritt entfernenREMOVED (gesperrt, solange andere Knoten seine Variablen lesen)

Neue Schleife in der Range-Form autemosRange(from, to, step, max)ADDED loop mit Bereich, Maximalzahl der Durchläufe und Variablenname
If-Block oder Schleife löschenREMOVED des Steuerknotens; verbliebene Kind-Schritte werden verschoben, gelöschte entfernt

Prüfregeln

  • Je If-Knoten höchstens eine true- und eine false-Verbindung, je Schleife genau eine Körper-Verbindung; keine Zyklen ausser der Rückkante der Schleife; alle erzeugten Knoten vom Start erreichbar; Verschachtelungstiefe höchstens 5.
  • Sub-Workflow-Referenzen müssen existieren, im gleichen Projekt liegen, aktiv und als Sub-Workflow gekennzeichnet sein und dürfen sich nicht (auch nicht indirekt) selbst aufrufen.
  • Die Übernahme bleibt atomar mit Versionen und Audit-Eintrag.

Grenzen

  • Strukturänderungen werden nur für Java/Playwright synchronisiert; in anderen Sprachen und Frameworks ist nur die Reihenfolge übernehmbar, Strukturänderungen sind als nicht unterstützt gekennzeichnet.
  • Nicht unterstützt: else if, switch, ternäre Ausdrücke, freie Ausdrücke, Operatoren ausserhalb der elf Operatoren des If-Knotens, while, do, for(;;), break/continue, Datensatz-Quellen bei Schleifen, Inputs aus Secrets, Bindings oder Datenbündeln, Variablen als Input, Änderungen an den Schritten innerhalb der Sub-Workflow-Methode sowie Tiefe über 5.
  • Ausführung in Autemos: Die Workflow-Engine wertet Bedingungen und Schleifen genauso aus wie der generierte Test. Bei einer Bedingung läuft nur der zutreffende Zweig, eine Schleife durchläuft jeden Eintrag ihres Bereichs. Eine Schleife ohne gültige Datenquelle bricht mit einer klaren Meldung ab.
  • Bedingung auf eine nicht gesetzte Workflow-Variable: Der generierte Test bricht mit «workflow variable <name> is not set» ab, statt still den Text zu vergleichen (Ausnahme: isEmpty/isNotEmpty).

Für Java/Selenium sowie TypeScript, Python und C# (je Playwright oder Selenium) erzeugt Autemos weniger:

Neue Aktionen

  • selectCombobox: natives <select> per Label, sonst Öffnen und Auswahl der Option mit exaktem Label (Rückfall Teiltext).
  • hoverAndClick, goBack, goForward, reload, rightClick, dragDrop als je eine Aktion; waitFor für «appears» und «disappears»; extractText speichert Text oder Attribut in eine Workflow-Variable.
  • Ziele sind ein Selektor oder ein Feld eines PageObjects. Fehlt beides oder gibt es das PageObject nicht im Projekt, entsteht eine begründete Lücke statt eines Zugriffs ins Leere.
  • wait: Die Einheit des Knotens (ms oder s) wird korrekt umgerechnet; Variablen als Dauer werden zur Laufzeit gelesen.

Gekennzeichnete Lücken

Enthält ein Test mindestens eine Lücke, steht als erste Zeile der Testmethode der Kommentar UNVOLLSTAENDIG: n Schritt(e) nicht generiert – siehe GENERATION_ERRORS.txt. Die Datei GENERATION_ERRORS.txt im Export nennt je Workflow, wie viele Schritte fehlen, und für jede Lücke den Grund. Code-Export

API-Schritte im Export

Der Java/Playwright-Export erzeugt für die Knoten apiRequest, apiVerify und apiExtract lauffähigen Code statt «NICHT GENERIERT». Für andere Sprachen und Frameworks bleibt es bei der Warnung «API-Schritte werden derzeit nur für java/playwright erzeugt».

  • Gemeinsame Sitzung: Alle API-Requests laufen über denselben Browser-Kontext wie der Browser. Cookies gelten dadurch in beide Richtungen, z. B. Login per API und danach eingeloggt im Browser. Ein Client-Zertifikat des Workflows gilt automatisch auch für API-Requests.
  • Authentifizierung kommt aus dem Knoten oder der Auth-Konfiguration: Bearer, Basic, API Key und OAuth2 (Client Credentials, mit einmaligem Wiederholen bei 401).
  • Geheimnisse stehen nie im Code. Ein Secret wird als Umgebungsvariable AUTEMOS_SECRET_<NAME> referenziert, der Name in Grossbuchstaben. Klartext-Werte sensibler Header (z. B. Authorization, Cookie, X-Api-Key) werden nicht übernommen, sondern als Umgebungsvariable AUTEMOS_HEADER_<NAME> erzeugt, mit Warnung. Fehlt eine Variable, bricht der Test mit einer klaren Meldung ab; die benötigten Variablen stehen im Kopfkommentar der Testmethode.
  • Gemerkte Werte: Per apiExtract gespeicherte Werte (Tokens, IDs) landen in den Workflow-Variablen und stehen späteren Schritten, auch Browser-Schritten, zur Verfügung. Die Antwort ist unter ihrem Alias und unter lastResponse abrufbar.
  • apiVerify unterstützt Status, JSONPath (mit denselben Operatoren wie die Laufzeit), teilweisen und exakten Body-Vergleich sowie eine maximale Antwortzeit. Die Prüfart «schema» (JSON-Schema) bleibt «NICHT GENERIERT» mit Warnung. Bei «soft failure» werden Fehler gesammelt und am Ende geworfen.
  • Der Export enthält die benötigte JSONPath-Bibliothek in der pom.xml. Nicht auflösbare Auth-Konfigurationen führen zu einer Lücke mit Warnung, nie zu geratenem Code.

Selektoren im erzeugten Code

Steht ein Selektor im erzeugten PageObject-Code, schreibt Autemos ihn als gültiges Literal der Zielsprache, dessen Wert zur Laufzeit genau dem gespeicherten Selektor entspricht. Sonderzeichen im Selektor machen den Code nicht mehr unübersetzbar.

ZielMaskiert werden
TypeScript (Backtick-Literal)Backslash, Backtick und ${
Java und C# (Literal in doppelten Anführungszeichen)Backslash und doppeltes Anführungszeichen
Python (Literal in einfachen Anführungszeichen)Backslash und einfaches Anführungszeichen
  • Das gilt für alle Selektorfelder der PageObjects, also auch für Android- und iOS-Locatoren und für Felder, die aus Ihrer Feldvorlage entstehen.
  • Der Code-Sync liest diese maskierten Literale wieder zurück. Ein unmaskiertes ${…} in einem TypeScript-Backtick-Literal (Interpolation) oder eine andere Maskierung wird als nicht synchronisierbar gemeldet.
  • Zeilenumbrüche und Tabulatoren in Selektoren werden nicht maskiert.
