Getting Started

Code Generation

The Code Generation Hub enables teams to automatically generate reusable automation code from Autemos workflows and PageObjects. It bridges the gap between visual low-code test design and developer-driven source code management — producing production-ready automation frameworks aligned with your existing technology stack.

Code Generation Hub — Dashboard with an at-a-glance overview of Framework, Project Structure and Sync Profiles.

Core Capabilities

Automatic Code Generation

Generate reusable automation code directly from test workflows, PageObjects, field definitions and actions.

Framework-Compliant Output

Generated code follows framework conventions, project structure rules, naming standards and template definitions.

Git Synchronization

Push generated code directly to a GitHub repository — with branch management and history tracking.

Sync Profiles

Create reusable synchronization configurations for automated, event-driven or scheduled code delivery.

Code Sync

Code Sync: State and Check

Once the generated test code of a workflow has been transferred to a GitHub repository with Push to Git, Autemos detects when that code is later changed by hand in the repository. The workflow is never changed silently: changes are shown and only applied after an explicit decision. When the state is unclear, Autemos never shows "In sync" by mistake.

⚠️GitHub only. Code Sync and Push to Git currently support GitHub only. GitLab and Bitbucket are disabled in the Git connection and rejected by the server.

Sync state in the workflow list

If the project has a Git connection, the workflow list (table and cards) shows the sync state of each workflow. The state is loaded after the list and never blocks it. Without a Git connection there is no column, no badge and no button.

StateMeaning
Not syncedThe workflow has never been transferred to the repository.
PR openThe pull request of the last Push to Git is still open. The workflow only counts as "In sync" after the merge.
In syncThe test file in the repository matches the last transferred version.
Out of syncThe test file was changed or deleted in the repository. Marked "ignored" if the change was deliberately ignored.
Baseline acceptedThe repository state was accepted as the new baseline, but the workflow was not updated from it.
UnknownThe state could not be checked (for example GitHub unreachable, invalid token, quota exhausted, or pushed before version tracking existed). The reason is shown in the tooltip.

The check only compares the test files of the respective workflow; commits to other files do not cause "Out of sync". The result is cached for about 10 minutes. The Check now button in the list header triggers the check immediately.

Notice in the workflow editor

In the workflow editor, the "Code sync" indicator in the toolbar shows the current state (an icon; the "Code sync: …" tooltip shows the state, the time of the last check and the latest commit). If the repository has changed, the notice There are changes in the underlying code appears with commit, author and time, plus a View changes button. If the change was ignored, the notice is more subtle and appears in full again after a new commit. If the state is unknown, Code sync state unknown appears with the reason.

"Code changes" dialog

The dialog shows the last synchronized code on the left and the current state in the repository on the right. At the top is the Workflow changes area: the detected changes per workflow node (node name, parameter, old and new value). Below it is the text diff of the code between the last synchronized version and the current repository state, marked per file as added, removed or changed. Exactly the lines that a git diff reports as added (green, right) or removed (red, left) are highlighted; a newly added node block is highlighted with all its lines, and the line before it stays unmarked. Below the comparison, Changed lines (from line n) lists the changed lines. Changes that cannot be applied are marked explicitly with the reason; pure comment and blank-line changes are marked as insignificant. The Supported changes link opens, in a new tab, the documentation shipped with Autemos for the supported changes (languages, frameworks, node types, limits); it does not need access to GitHub.

Decisions

ButtonEffect
Ignore changesThe workflow stays unchanged. The state remains "Out of sync (ignored)" until a new commit arrives.
Accept baseline onlyThe repository state becomes the new baseline; the workflow stays unchanged. The state is "Baseline accepted", not "In sync".
Apply to workflowApplies the detected changes to the workflow. After a confirmation ("Apply code changes to workflow?") the workflow is updated and the state changes to "In sync".
Check nowChecks the repository again immediately and updates state and preview.
Push to GitRegenerates the workflow code and opens the pull request dialog (see "Push to Git from the editor").
CloseCloses the dialog without changing anything.

Rules for "Apply to workflow"

  • The button is disabled (with a reason) as long as a change is unsupported, the code could not be analysed, a conflict exists or the preview is not available. Nothing is ever applied partially.
  • Applying is atomic: either everything is applied or nothing. Before applying, Autemos creates a restorable version "Before code sync apply (commit …)" and afterwards "Applied code changes from commit …". Both are identifiable in the version history with the source "Code sync".
  • If the workflow was edited in Autemos since the last sync, or someone else is editing it right now, the preview reports a conflict and overwrites nothing. If the repository changed again after the dialog was opened, Autemos rejects the decision with a hint to reload.
  • The resulting workflow structure is validated before saving. Node types the generator does not produce are preserved in the workflow.
  • If an earlier version of the workflow is restored, the sync state changes to "Out of sync".
  • The preview is only available if the test file comes from an Autemos version that contains node markers. For older states, "Preview not available" appears; a new Push to Git fixes this. Ignoring and accepting the baseline remain possible.
  • Project members can view the preview. Applying and deciding require editor rights. All steps (preview viewed, applied, conflict, restored, decision) appear in the audit overview in the "Code Sync" category.
💡What runs is always the workflow in Autemos, never the code from the repository. An "Out of sync" workflow therefore keeps running unchanged until the changes have been applied.

Notice after "Apply to workflow": new node IDs

If "Apply to workflow" created new steps, the code in the repository still says node=new, while the new nodes in Autemos already carry a unique ID. Until the code has been transferred again, the workflow editor shows a lasting notice above the workflow: Workflow updated. New nodes have been assigned unique IDs. with the sentence "Please synchronize the generated code with GitHub before making further external changes." and the Sync code now button.

  • Sync code now opens the "Push to Git" dialog for this workflow. The run only starts when you click Create Pull Request; Autemos never changes the repository by itself. The button is disabled (with a reason) if the workflow has unsaved changes or the project role does not allow editing.
  • The notice stays after a reload and for other users, also in the state "In sync". It disappears as soon as the pull request has been created (the state "PR open" does not show it). A later apply that only changes parameters does not clear it.
  • The notice appears only if at least one new step was applied; it does not appear after pure changes or removals.
  • As long as it is shown, the "Code changes" dialog warns above "Workflow changes": steps from an earlier apply still carry node=new in the repository, so with further external changes they may appear as added and removed at the same time. Applying remains possible; synchronize the code first.
  • After the apply, a short message says: "Sync the generated code with GitHub – see the notice above the workflow."
Code Sync

Push to Git from the Workflow Editor

From the "Code changes" dialog in the workflow editor, the Push to Git button generates the code of the open workflow and a GitHub pull request without leaving the editor. It opens the same Push to Git dialog as the Generate tab; only the open workflow and the PageObjects it uses are passed on.

  • The button is disabled while the workflow has unsaved changes ("Save your changes before pushing to Git") or when the project role does not allow editing ("You need editor rights in this project to push to Git").
  • Before the push, Autemos checks the repository afresh. If the repository has external changes that are not in the workflow yet, the state is unknown or the accepted baseline differs, a warning appears and Create Pull Request stays disabled until the checkbox Overwrite the external changes in the repository is ticked. View changes jumps to the "Code changes" dialog. External changes are therefore never overwritten unnoticed.
  • For ignored changes or a pull request that is still open, only a note appears and the push stays free.
  • After success, a notice Pull request #n created – not merged yet appears and the indicator changes to "Code sync: PR open".

Open pull request and missing Git connection

  • Open pull request: As long as the pull request is not merged there is nothing to compare. The "Code changes" dialog then shows an information with the link Open pull request #n instead of a red error and without a retry button. Genuine loading errors still appear as errors with Retry.
  • No Git connection: The editor shows "Code sync: not set up". The dialog explains "No Git connection is configured for this project." and offers the link Set up Git connection, which leads directly to the setup in the Code Generation Hub. Push to Git is disabled until then ("Set up a Git connection first").
Code Sync

Supported Code Changes

Code Sync reads changes to the generated test code back node by node. In the generated code, each workflow node sits between the marker comments @autemos node=… type=… and @autemos end. These markers assign the code to the node and must not be removed or modified. A new step is introduced with @autemos node=new type=….

Change kinds

KindMeaningCan be applied
MODIFIEDA parameter of a node changed (old → new value).Yes
ADDEDA new step was added in the code.Yes, if the form is supported
REMOVEDA step was removed from the code. If the step or its variable is still read by other nodes, applying is blocked.Yes
REORDEREDThe order of the steps changed.Yes
MOVEDA step is in another branch, inside or outside a loop body, or on another level.Yes (Java/Playwright)
UNSUPPORTEDA change that cannot be synchronized, with a reason. Blocks "Apply to workflow".No
IGNORABLEComment or blank lines only.No effect

New steps

New steps (ADDED) are applied for navigate and wait in all languages. Only for Java/Playwright, ifCondition, loop and callSubWorkflow are added, and, in the page.locator form, click, doubleClick, hover, check, pressKey, scroll, type, select and assert. The new node receives the selector from the statement. A new step that addresses a PageObject element cannot be applied ("new steps via a page object need the element mapping"), because Autemos cannot assign the element from the code; use the page.locator("…") form or create the step in Autemos.

Selectors in PageObject files

If someone changes the selector of a field in a PageObject file generated by Autemos, the sync shows the change on every node that uses this field. Apply to workflow writes the new selector to the PageObject field in Autemos. This applies to web PageObjects with Playwright in Java, TypeScript, Python and C#. Fields are assigned through @autemos pageObjectField=… markers; fields are created, renamed and removed in Autemos, not in the code (a duplicated marker or a modified locator literal is reported as a problem). In TypeScript, fields with multi-platform locators (for example only an Android or iOS locator) cannot be synchronized. Selector changes directly in the test (page.locator("…")) are recognized but not applied.

Each workflow watches the PageObject file in its own target folder. If you transferred the same PageObject from two workflows into different target folders, these are two separate files: a change in one file is shown only by the workflow whose folder it concerns, and a later further change to the same field is also detected with Check now. If several workflows use the same PageObject, the reason of the change names the other workflows (also used by: …, at most five names, then +n more), because Apply to workflow changes the selector for all of these workflows.

Code Sync

Structure Changes: Conditions, Loops, Sub-Workflows

Conditions, loops and sub-workflow calls appear in the generated Java/Playwright code in an unambiguous way (with their own markers for branches and loop bodies). The preview shows changes to them individually, including the affected connections (the Connections and Sub-workflow references areas). Only what results in a valid workflow structure is applied; otherwise the change is marked and "Apply to workflow" is disabled.

Change in the codeResult
Step into another branch, into or out of a loop body, another levelMOVED, connections are rebuilt
Reorder steps within one levelREORDERED
New step in a branch or loop bodyADDED with structure path (for example "if1 › true")
Remove a stepREMOVED (blocked while other nodes read its variables)
New if block in the generated form autemosCondition("…","operator","…"), with optional elseADDED ifCondition with condition, operator and comparison value
New loop in the range form autemosRange(from, to, step, max)ADDED loop with range, maximum iterations and variable name
Delete an if block or loopREMOVED of the control node; remaining child steps are moved, deleted ones are removed
Add or remove an else branchChange of the connections
Add a sub-workflow callADDED callSubWorkflow (prerequisite: the method autemosSub_<id> exists in the code)
Remove a sub-workflow callREMOVED (blocked while its output variables are read)
Point a call at another sub-workflowMODIFIED workflowId; contract and snapshot are re-read from the target. An invalid target blocks applying.
Add or remove input mappingsCan be applied for literals; a mandatory input must not be dropped
Output mappingsChange, add, remove the target variable; with reader check
Loop variable (variableName)MODIFIED with reader check: if the old variable is still read, applying is blocked

Validation rules

  • At most one true and one false connection per if node, exactly one body connection per loop; no cycles except the loop's back edge; all generated nodes reachable from the start; nesting depth at most 5.
  • Sub-workflow references must exist, be in the same project, be active and marked as sub-workflow, and must not call themselves (not even indirectly).
  • Applying stays atomic with versions and an audit entry.

Limits

  • Structure changes are only synchronized for Java/Playwright; in other languages and frameworks only the order can be applied, structure changes are marked as unsupported.
  • Not supported: else if, switch, ternary expressions, free expressions, operators outside the eleven operators of the if node, while, do, for(;;), break/continue, dataset sources for loops, inputs from secrets, bindings or data bundles, variables as input, changes to the steps inside the sub-workflow method, and depth beyond 5.
  • Execution in Autemos: the workflow engine evaluates conditions and loops the same way as the generated test. Only the matching branch of a condition runs, and a loop runs once for every entry in its range. A loop without a valid data source stops with a clear message.
  • Condition on an unset workflow variable: the generated test aborts with "workflow variable <name> is not set" instead of silently comparing the text (exception: isEmpty/isNotEmpty).

Other languages and frameworks

For Java/Selenium and for TypeScript, Python and C# (each with Playwright or Selenium), Autemos generates less:

  • Generated as code: navigate; type, click and select when the step addresses a PageObject element; wait; screenshot; the test data nodes. An assertion (assert) is generated only as an equality comparison, with a placeholder for the actual value and a warning; without an expected value a gap results. Framework nodes and timeGap appear as a comment.
  • Gap with the comment "NICHT GENERIERT" and a warning: all other node types (for example doubleClick, hover, check, pressKey, scroll, selectCombobox, hoverAndClick, goBack, goForward, reload, rightClick, dragDrop, waitFor, extractText, table, API and flow nodes such as ifCondition, loop, callSubWorkflow) as well as type, click and select without a PageObject element (note "Locator form only for java/playwright").

New actions

  • selectCombobox: native <select> by label, otherwise open the control and choose the option with the exact label (fallback: partial text).
  • hoverAndClick, goBack, goForward, reload, rightClick, dragDrop as one action each; waitFor for "appears" and "disappears"; extractText stores text or an attribute in a workflow variable.
  • Targets are a selector or a field of a PageObject. If both are missing or the PageObject does not exist in the project, a justified gap is produced instead of a dangling access.
  • wait: the unit of the node (ms or s) is converted correctly; variables as duration are read at run time.
  • Start URL: the test starts with the URL of the first openBrowser node, otherwise the first navigate node, otherwise about:blank. If the URL contains a variable, about:blank is used and the variable is resolved when navigating.

Marked gaps

If a test contains at least one gap, the first line of the test method is the comment UNVOLLSTAENDIG: n Schritt(e) nicht generiert – siehe GENERATION_ERRORS.txt. The file GENERATION_ERRORS.txt in the export states per workflow how many steps are missing and gives the reason for each gap. The "Supported changes" page of the in-app documentation contains the table Code generation support with one row per node type.

Code Export

API Steps in the Export

For the nodes apiRequest, apiVerify and apiExtract, the Java/Playwright export produces executable code instead of "NICHT GENERIERT". For other languages and frameworks, the warning "API-Schritte werden derzeit nur für java/playwright erzeugt" remains.

  • Shared session: all API requests run through the same browser context as the browser. Cookies therefore apply in both directions, for example login via API and then logged in in the browser. A client certificate of the workflow automatically applies to API requests as well.
  • Authentication comes from the node or the auth configuration: Bearer, Basic, API Key and OAuth2 (client credentials, with one retry on 401).
  • Secrets never appear in the code. A secret is referenced as the environment variable AUTEMOS_SECRET_<NAME>, with the name in upper case. Plain-text values of sensitive headers (for example Authorization, Cookie, X-Api-Key) are not copied but generated as the environment variable AUTEMOS_HEADER_<NAME>, with a warning. If a variable is missing, the test aborts with a clear message; the required variables are listed in the header comment of the test method.
  • Remembered values: values stored with apiExtract (tokens, IDs) end up in the workflow variables and are available to later steps, including browser steps. The response can be retrieved under its alias and under lastResponse.
  • apiVerify supports status, JSONPath (with the same operators as at run time), partial and exact body comparison and a maximum response time. The check type "schema" (JSON Schema) remains "NICHT GENERIERT" with a warning. With "soft failure", errors are collected and thrown at the end.
  • The export contains the required JSONPath library in the pom.xml. Auth configurations that cannot be resolved lead to a gap with a warning, never to guessed code.

Selectors in the Generated Code

When a selector appears in the generated PageObject code, Autemos writes it as a valid literal of the target language whose value at runtime is exactly the stored selector. Special characters in the selector no longer make the code uncompilable.

TargetEscaped
TypeScript (backtick literal)Backslash, backtick and ${
Java and C# (literal in double quotes)Backslash and double quote
Python (literal in single quotes)Backslash and single quote
  • This applies to all selector fields of PageObjects, including Android and iOS locators and fields created from your field template.
  • The code sync reads these escaped literals back. An unescaped ${…} in a TypeScript backtick literal (interpolation) or any other escape is reported as not synchronizable.
  • Line breaks and tabs in selectors are not escaped.
