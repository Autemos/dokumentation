Test Workflows

Test Workflows are the central building block for automated testing in Autemos. They provide a visual, node-based representation of test logic, enabling users to efficiently design, customize, and debug automated tests.

A typical workflow consists of sequential steps such as opening an application, interacting with UI elements, validating results, and managing data. While most workflows are linear, Autemos also supports conditional logic and loops for more advanced testing scenarios.

The Test Workflows overview lists all existing tests with list/tile view and search options.

What You Can Do With Test Workflows

  • Refine recorded tests and add custom logic
  • Add validations and assertions to verify application behavior
  • Integrate test data for dynamic, reusable scenarios
  • Debug execution step by step with breakpoints and live view
  • Ensure test readiness before automated headless execution
The visual canvas — each step is represented as a node that performs a specific action.

Creating and Editing

The Test Workflows overview lists all existing tests. The + New Workflow button opens an empty canvas. The Record Workflow button navigates to the recording module, where tests can be created with a click recorder or an AI chatbot. Workflows can be toggled between list and tile view, searched, sorted, and selected.

Each step in the workflow is represented by a node that performs a specific action, such as clicking an element, entering text, or validating a condition.

Test Workflows and Sub-Workflows

Test Workflows are the primary executable tests in Autemos. They combine browser, mobile, API, data and validation steps into an end-to-end test process.

Sub-Workflows are reusable workflow components that can be called from one or more Test Workflows. They are suitable for frequently repeated processes such as login, customer creation, navigation, test data preparation or cleanup.

Using Sub-Workflows reduces duplicated test steps, simplifies maintenance and ensures that shared processes are implemented consistently across multiple tests.

Understanding Nodes

Nodes are the basic units of a Test Workflow. Each node represents a single action or operation:

  • Interact with UI elements (Click, Type)
  • Capture information (Extract Text, Screenshot)
  • Validate behavior (Assert, Soft Verify)
  • Manage data (Test Data, input variables)
  • Control flow (If, Loop, Wait)

Nodes can interact with variables and stored data depending on their type. Detailed documentation for each node is available in the node reference sections below.

Working With Test Data and Variables

Test Workflows support flexible data management for dynamic and reusable tests. Data can be stored in variables, cached during execution, and reused in later steps.

  • Store values in workflow variables and reuse them across steps
  • Use the Test Data Easy node to bind tabular data sets inline
  • Access row data via {{easyData.field}} or {{easyDataRecords.0.field}}
  • Link externally managed data sets for cross-workflow reuse

Supported Test Types

Test Workflows support multiple test types within a single flow — independently or combined:

  • Web Testing — browser-based UI automation
  • Mobile Testing — iOS and Android app tests
  • API Testing — direct HTTP request validation

This enables end-to-end scenarios such as: mobile action → API validation → web verification.

Create Your First Test Workflow in 5 Minutes

This quick tutorial walks you through creating, refining, and debugging a simple Test Workflow in Autemos. By the end, you will have a working, test-ready workflow.

1

Open a Test Workflow

In the demo project, you will find sample tests for Mobile, Web, and a combined flow. After selecting a test, you will see the workflow canvas, where each step is represented as a node. Recorded workflows typically include application launch, basic user interactions, and navigation steps.

2

Review the Workflow Structure

Scan the workflow from top to bottom. Look for a clear step sequence (e.g., Login → Navigate → Action), missing validations, and hard-coded or unclear values. At this stage, most workflows are functional but not yet robust or reusable.

3

Add a Validation

After an important action, add an Assert or Soft Verify node to check that a screen is visible, a value is correct, or an element is present.

💡Use Soft Verify when the test should continue even if a check fails.
4

Introduce Test Data

Replace static values with dynamic data using the Test Data Easy node. Insert the node directly after the start node at the beginning of the workflow. This allows your workflow to run with different data sets and to be reused across scenarios.

5

Clean Up and Structure

Rename nodes for better readability (e.g., "Click Button" → "Click Login"), mentally group logical steps (Login, Navigation, Action), and remove unnecessary steps. A clean workflow is easier to debug and maintain.

6

Debug the Workflow

Switch to debug mode. Set a breakpoint at a critical step, run the workflow, step through it, and observe the behavior in the live view. Use the execution log to check timing, success/failure, and errors. Fix issues immediately.

7

Confirm Test Readiness

Your workflow is ready when: all steps execute successfully, validations are in place, test data is correctly configured, and no blocking errors occur during debugging. The workflow can now be reliably executed in automated runs via the Scheduler.

Error Handling & Soft Verify

Workflows support flexible error handling strategies.

Default Behavior

By default, a workflow stops execution when a step fails. This is the safest option and ensures that issues become immediately visible.

Soft Verify

When using Soft Verify, errors are logged and execution continues. This is useful when multiple validations should run and you want a complete test result instead of an early termination.

A failed step displays the error details inline — XPath or selector issues are shown directly on the node.

When to Use Which Approach

Default (Stop on Failure)

Use this when a step failure makes all subsequent steps pointless. For example, if login fails, continuing makes no sense.

Soft Verify (Continue)

Use this when you want to collect all validation errors in a single run, e.g., for form field validations or UI state checks.

Prepare a Workflow for Execution

Before a workflow can be executed automatically in headless mode (e.g., in a scheduler), it must be test-ready. A test is considered ready when:

  • All steps execute successfully
  • Data dependencies are resolved
  • No blocking errors remain

Collections (Test Sets)

A Collection is an ordered group of Test Workflows that you run together: via Fast Run or as the target of a schedule, sequentially or in parallel, with automatic retry of failed tests. Each run is its own Collection Execution with a report per test and an overall status. Collections work without any Jira/Xray configuration.

Creating a Collection

  • The workflow overview has a Collections (n) tab next to All, Test-Workflows and Sub-Workflows.
  • The header is the same in every tab: view toggle, Record Workflow and the + Create menu with the entries Workflow, Sub-Workflow and Collection.
  • + Create → Collection opens the Create Collection dialog with the fields Name and Description, a search (Search workflows) and the list of all Test Workflows of the project (sub-workflows are not listed). Each workflow shows its version, Jira key and last-changed date.
  • The order in which you tick the workflows is the order of the collection. Create saves the collection and opens its detail page.

Collection List and Detail Page

The list in the Collections tab shows Name, Workflows, Last execution, Status and Updated. Every row has a Run button; clicking the name opens the detail page.

Rules

  • All workflows that are part of the collection and available at the time of the start are executed. Workflows added later are not part of that execution.
  • Unavailable members are reported before the start and shown as Not run (reason “Workflow unavailable”) in the report.
  • In Parallel mode, by default at most three tests run at the same time; further tests start as soon as a slot becomes free.
  • Only failed tests are repeated, at most Retry count times. With Sequential, the retry runs before the next test. Self-healing works unchanged inside each run.
  • Creating, changing and running requires project membership; reading requires project access.

The page “<Collection> – execution #<id>” shows the overall status (Overall status), mode, retry, trigger, start and end, and a summary such as “n passed · m failed · k not run”. While the execution is running it refreshes every 5 seconds; Cancel stops a queued or running execution. The Test results table has the columns Test, Status, Attempts, Duration (sum of all attempts) and Report with an “Attempt n” link per attempt to the run report.

Auto Connect

The Auto Connect button in the toolbar suggests connections for unconnected nodes when their arrangement is unambiguous. Existing edges and node data stay untouched.

  • The suggested edges appear dashed. The Auto Connect proposal bar reports, for example, “2 connections suggested”.
  • Only Apply accepts the proposal; Cancel discards it without any change.
  • After Apply, a single Undo reverts all new edges.
  • Ambiguous places are not connected but reported: open outputs of If and Loop, positions of equal rank and areas with several ends.
  • If nothing is unambiguous, “No unambiguous connections …” appears with a Close button.
  • The button is disabled while the editor is locked, a run is active or fewer than two nodes exist.
💡Auto Connect prefers to connect nothing rather than connect wrongly. Review the dashed proposal before Apply.
Editor & Execution

Red Nodes: Finding the Reason

A node with a red outline is incomplete or unreachable. The reason is visible directly in the editor, for all node types:

  • On the node: hovering shows a tooltip with the concrete message.
  • In the node details: every missing required field is marked red at its own form field, and the message below it states which value is missing. For the Extract Text node, for example, this is the Save As field when it is empty, not just the source element.
  • For orphan nodes (unreachable) and nodes of unknown type there is only the tooltip, because no single field is affected.

The rules about which fields are required do not change; the display only makes the already computed reason visible. A validly configured node stays unmarked.

Date and Calculation Expressions in Placeholders

In addition to variables and test data, the {{…}} placeholders accept two kinds of expressions that are evaluated at run time. A workflow replayed on another day therefore yields the correct date instead of a frozen literal.

ExpressionMeaningExample
{{today}}, {{now}}Today’s date or the current point in time{{today}}
{{today+3d}}Offset ±N with unit d (days), w (weeks), m (months) or y (years){{today-1w}}
{{today+3d|dd.MM.yyyy}}Optional output format after | (date pattern)Delivery date in 3 days as dd.MM.yyyy
{{a+b}}, {{price*2}}Simple arithmetic with numbers and numeric variables{{2+3}}
  • An ordinary variable always takes precedence: if a variable is called today, its value is used rather than the date.
  • The AI recorder writes a relative date request (“delivery date in 3 days”) as an expression, not as a resolved date.
  • There is no full formula language: no parentheses and no functions beyond the forms listed.
  • Workflows already recorded with frozen date values are not rewritten.

Sub-Workflows

Sub-Workflows allow reusable sequences of test automation steps to be created once and used across multiple Test Workflows.

Instead of repeating the same actions in every test, a shared process can be maintained as a separate Sub-Workflow and inserted through a Call Sub-Workflow node.

Typical Examples

  • Logging in to an application
  • Creating or preparing test data
  • Navigating to a frequently used application area
  • Completing a reusable business process
  • Performing common validation or cleanup steps

When a Sub-Workflow is updated and saved, the embedded snapshot used by its parent workflows is refreshed automatically.

Benefits

  • Reduced duplication across Test Workflows
  • Central maintenance of shared test sequences
  • More consistent automation behavior
  • Smaller and easier-to-understand parent workflows
  • Reusable processes with configurable input parameters
  • Controlled exchange of values between parent and child workflows

Parameters and Variable Scope

Sub-Workflows can define optional input parameters through the Parameters node. Configured parameters are available across the whole Sub-Workflow and appear automatically on the parent Call Sub-Workflow node.

Parameters represent the values that a parent workflow is allowed to pass into the Sub-Workflow. Each parameter can define a default value that remains active when the parent workflow does not provide an override.

💡Parameters are optional. A Sub-Workflow with no configured parameters can be used without inputs.

Input Behavior

  • Only explicitly declared child parameters are available for mapping.
  • A parent value can be provided as a static value, binding or secret.
  • A value provided by the parent overrides the child default.
  • If no parent value is assigned, the child default remains active.
  • Unmapped parent variables do not automatically enter the child scope.

Output Behavior

  • Child variables remain isolated from the parent by default.
  • Only explicitly mapped outputs are returned.
  • Each returned value is assigned to a cache variable name in the parent workflow.
  • Internal child variables are not exposed unless configured as outputs.

Parameter Types: Text, Secret, Data Bundle

In the Parameters node every row has a type (Parameter type): Text (default), Secret or Data Bundle. Secret and Data Bundle have no default value; the field shows “Assigned by the calling workflow”. Existing parameters stay Text.

  • In the calling Call Sub-Workflow node (section Input Parameters) you pick an existing secret for a Secret parameter and a test data binding of the project for a Data Bundle parameter (Data bundle for <parameter>). Assignments that no longer exist are highlighted (“Secret “X” is not available in this project.”).
  • Inside the sub-workflow the steps use {{param}} (secret value), {{param.field}} (field of the first record) or {{paramRecords}} (list of all records).
  • Type and availability are checked before the sub-workflow starts; an error aborts the call node with a clear message, for example “Sub-workflow parameter "zugang" expects a secret, but a binding was assigned.”, “… (data bundle) is required, but nothing was assigned.” or “… secret "KK_PWD" does not exist or is not accessible for this run.”
  • Secret values appear masked in the log, the report and the output of the call node.

Updates and Snapshots

A Call Sub-Workflow node does not execute the child workflow by reference, but through an embedded snapshot stored on the node.

  • The snapshot contains the executable child workflow structure.
  • Saving the child Sub-Workflow refreshes the snapshot used by parent workflows.
  • Parent workflows use the latest saved state of the child.
  • Unsaved child changes are not available to parent workflows.
  • The Open Child action opens the source Sub-Workflow directly.

For verification, the node shows the capture time (Captured) and the size of the snapshot in nodes (Snapshot Size).

💡Only workflows explicitly marked as Sub-Workflows can be selected in the child workflow field.

Closed Shadow DOM

Session Control

Elements in closed shadow roots (attachShadow({ mode: 'closed' })) are found and operated with the same selectors as elements in open ones: CSS (#target-4), text (text=Click target 4) and role (role=button[...]). There is no separate selector syntax and no workaround in page objects; recorder, self-healing and code export work unchanged.

How It Works

  • The Open Browser node installs a small hook in Playwright web sessions that creates closed shadow roots as open ones internally. It applies to all pages and frames loaded afterwards.
  • The host element then carries the attribute data-stk-shadow-was-closed, so the original encapsulation remains recognisable.
  • The worker notes in the run log that the feature is active.

Limits

  • Applies to Chromium and Edge (via the grid); Selenium mode and mobile sessions are not affected.
  • The target page sees the root as open. Pages that check whether shadowRoot is null may behave differently.
  • A document that is already loaded is only covered from the next navigation.
  • A Playwright test outside Autemos that does not install this hook does not find these elements.

Switching It Off

The feature is on by default. The worker setting WORKER_CLOSED_SHADOW_FORCE_OPEN=false switches it off; the earlier behaviour then applies (elements in closed roots are not found), and the log notes that the feature is off.

  • you have to wait for external systems
  • you build multi-part workflows

  • future workflow continuations are scheduled
  • retry or follow-up workflows are required

  • Only users with the role Custom Code Author, or administrators, may create or change Custom Code. The role is set in addition to the normal role: in the dialog for creating and editing users via the Custom Code Author switch.
  • Without the role the palette entry is disabled (“Requires role Custom Code Author”), and Code, Outputs and Timeout are read-only. Moving, renaming, disabling, deleting and duplicating the node remain possible.
  • The server enforces this when saving, restoring and through the API: “Custom Code can only be created or edited by users with the role Custom Code Author or Administrator.”
  • This also applies to Custom Code in embedded sub-workflow images and to Run without saving: new or changed Custom Code is neither saved nor executed without the role (“This run contains new or changed Custom Code. Only users with the role Custom Code Author or Administrator can run it – save it with an authorized user first.”). Limits

  • query, queryAll and text take CSS selectors only; Playwright selectors (text=, >>) and XPath raise a SyntaxError.
  • iframes: the search does not look inside. For the same origin, iframe.contentDocument helps; frames of another origin are not reachable. Alternative: a Switch Frame before the block and Exit Frame after it.
  • Shadow DOM: open roots are reachable via host.shadowRoot, closed ones are not.
  • Navigation: if the code keeps running after a navigation (window.location, clicking a link), the step fails with “Execution context was destroyed, most likely because of a navigation” and its ctx.log lines are lost. Navigate as the last statement and add a Wait for step afterwards.
  • No page objects and no self-healing for these selectors.
  • The whole block is a single step in the report under the node’s name; the ctx.log lines appear behind “Show n log entries”.
  • Forbidden constructs (among others fetch, XMLHttpRequest, WebSocket, eval, setInterval, document.cookie, localStorage, import, require) are rejected during validation. This is a coding rule, not protection against circumvention.

Table Handling

Table Handling

The Table Handling Nodes provide a complete set of business-oriented operations for interacting with enterprise tables in your Test Workflows. Instead of relying on row positions or technical selectors, they work with business columns, conditions, and configured table definitions.

Invalid Arguments Are Rejected

A table node (and the table tools of the AI recorder) fails immediately with a clear message if a row condition is not valid, instead of silently running with a different meaning. The message names the field, the wrong value and the allowed values; no row is clicked or counted.

  • Criteria mode may only be all or any (for example OR is rejected; upper/lower case does not matter).
  • A comparison operator must be one of the supported ones (for example notEqual is rejected); if it is missing, equals applies. This also applies to the cell checks.
  • The conditions (criteria) must be a list; an object leads to “criteria must be a list of conditions …”. Empty is allowed.
  • A condition with a value but without a column is rejected (“criteria condition #n has no column”); a completely empty condition is ignored.
  • The same applies to saved workflows: the node is “failed” in the run before the worker is called. In the AI recorder the message appears as an error of the tool call.

Sort Table

Table Handling

The Sort Table Node applies or removes sorting for a business column in a configured table. Used to dynamically control table sorting without relying on technical header selectors or manual UI clicks.

When to Use

  • Sort table data by a business column
  • Change table sorting before validation
  • Prepare deterministic table states
  • Verify sorted records
  • Remove active sorting on a column

Table Verify

Table Handling

The Table Verify Node is the central verification node for table-based workflows. Used to validate table state, headers, columns, rows, counts, sorting, selection, cell values, and configured row actions in a single unified verification node.

When to Use

  • Verify table visibility or empty states
  • Validate table structure (headers, columns)
  • Verify row counts or row existence
  • Validate cell values
  • Check sorting behavior
  • Validate selected rows and configured row actions
💡This node centralizes most table-related validation scenarios into a reusable verification component.

Verification Types

Table State

Verify visibility, emptiness, or pagination state (has/no next page).

Column / Header

Verify that a specific business column or header exists in the table.

Row Count / Presence

Verify the number of rows or that a matching row exists.

Cell Value

Verify the value of a specific cell in a matching row.

Sorting

Verify that the table is sorted by a specific column and direction.

Row Action

Verify that a configured action exists on a matching row.

Behavior

  • Automatically uses table definitions, business columns, configured row actions, and pagination handling
  • Verification failures stop the workflow unless Soft Verify is enabled

Output
