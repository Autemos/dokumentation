Erste Schritte

Project Settings

Das Modul Project Settings zentralisiert die administrative Konfiguration eines Projekts. Es ermöglicht Projekt-Ownern und Administratoren die Verwaltung von Projekt-Metadaten, Umgebungen, Mitgliedern, API Keys sowie Authentifizierungs-Konfigurationen und Secrets.

Project Settings — zentrale Verwaltung aller projektbezogenen Konfigurationen.

Verwaltete Bereiche

Projekt-Metadaten

Name, Beschreibung und Grundkonfiguration des Projekts.

Projekt-Umgebungen

Applikationen und Environments (TEST / QA / PROD).

Mitglieder & Berechtigungen

Zugriffe und Rollen pro Projekt.

API Keys

Programmatischer Zugriff für externe Integrationen.

Auth & Secrets

Wiederverwendbare Auth-Konfigurationen und verschlüsselte Secrets.

Das Modul bildet die Grundlage für sichere Zusammenarbeit, Umgebungsmanagement und API-Integrationen innerhalb der Plattform.

Konfiguration

General Settings

Die Sektion General enthält die zentrale Projektkonfiguration inklusive Projektname, Beschreibung, Umgebungsverwaltung und Applikations-Katalog.

General Settings — Projektname, Beschreibung und Applikations-/Environment-Katalog.

Jedes Projekt definiert

Mehrere Anwendungen und Umgebungen, die verwendet werden für:

  • Test Workflows
  • Recorder Sessions
  • Test Data Bindings
  • API-Ausführungen

Wann verwenden

  • Beim Anlegen einer neuen Projektstruktur
  • Konfiguration von Testumgebungen
  • Verwaltung mehrerer Applikations-URLs
  • Trennung von TEST / QA / PROD Umgebungen
  • Aktualisierung der Projekt-Metadaten

Project Environments

Jede Applikation kann mehrere Umgebungen enthalten. Beispiel:

ApplicationEnvironmentURL
MigrosTESThttps://www.migros.ch/de

Unterstützte Aktionen

  • Applikation hinzufügen
  • Applikation entfernen
  • Environments hinzufügen
  • Environment-URLs definieren
  • Default-Environments konfigurieren

Verhalten

  • Environment-Konfigurationen werden zentral verwaltet
  • Workflows können dynamisch auf Environments referenzieren
  • Recorder- und API-Nodes verwenden die konfigurierten Environment-URLs
  • Änderungen wirken projektweit

Best Practices

  • Klare Naming-Konventionen für Environments verwenden
  • TEST, QA und PROD strikt trennen
  • Keine Produktions-Credentials in Test-Environments nutzen
  • Environment-URLs zentral pflegen
Konfiguration

Members

Die Sektion Members verwaltet den Projektzugriff und die Benutzerrechte.

Members — Übersicht aller Projektmitglieder mit ihren Rollen.

Benutzer können

  • Projekten zugewiesen werden
  • Aus Projekten entfernt werden
  • Bestimmte Rollen erhalten

Unterstützte Rollen

Rollenzuweisung — OWNER, ADMIN oder MEMBER pro Benutzer.
RolleBerechtigungen
OWNERVollständige Projektadministration
ADMINWorkflows, Settings und Benutzer verwalten
MEMBERErlaubte Ressourcen ausführen und bearbeiten

Wann verwenden

  • Projektzugriff gewähren
  • Team-Berechtigungen verwalten
  • Tester oder Entwickler onboarden
  • Administrative Zugriffe beschränken

Verhalten

  • Nur zugewiesene Benutzer können auf das Projekt zugreifen
  • Rollen bestimmen die verfügbaren Berechtigungen
  • Owners haben volle administrative Kontrolle
  • Members erhalten begrenzten operativen Zugriff

Best Practices

  • OWNER-Berechtigungen auf wenige Benutzer beschränken
  • MEMBER für Standard-Tester verwenden
  • Projektzugriffe regelmässig prüfen
  • Inaktive Benutzer entfernen
Integration & Security

API Keys

Die Sektion API Keys ermöglicht den sicheren programmatischen Zugriff auf die Plattform. API Keys können für externe Integrationen, CI/CD-Pipelines, Service Accounts und automatisierte Ausführungen verwendet werden.

API Keys — sicherer programmatischer Zugriff für externe Integrationen.

Wann verwenden

  • Integration externer Systeme
  • Automatisierte Ausführungen
  • Anbindung an CI/CD-Pipelines
  • Machine-to-Machine-Kommunikation

Configuration

API Key Konfiguration — Name, Beschreibung und Ablaufdatum.
ParameterBeschreibung
Key NameName des API Keys
DescriptionOptionale Beschreibung zur Verwendung
Expires InAblaufdauer in Tagen

Verhalten

  • API Keys werden sicher generiert
  • Der vollständige Key wird nur einmalig nach der Erstellung angezeigt
  • Abgelaufene Keys werden automatisch ungültig
  • Keys können jederzeit widerrufen werden
⚠️Sicherheitshinweis — Der vollständige API Key wird nur einmalig nach der Erstellung angezeigt. Speichere API Keys immer sicher ab.

Best Practices

  • Wo möglich Ablaufdaten verwenden
  • Keys regelmässig rotieren
  • Separate Keys pro Integration
  • API Keys niemals öffentlich exponieren

Environment Secrets

Environment Secrets — verschlüsselte sensitive Daten zentral verwaltet.

Environment Secrets speichern verschlüsselte sensitive Werte wie Tokens, Passwörter, Client Secrets und API Credentials. Secrets sind at rest verschlüsselt und werden nach der Erstellung nie wieder vollständig angezeigt.

Configuration

ParameterBeschreibung
KeySecret-Identifier
ValueVerschlüsselter Secret-Wert
DescriptionOptionale Beschreibung

Verhalten

  • Secrets sind sicher verschlüsselt
  • Werte bleiben nach Erstellung verborgen
  • Secrets können über mehrere Auth-Konfigurationen wiederverwendet werden
  • Werden von API Request Nodes und Integrationen verwendet

Auth Configurations

Auth Configurations — wiederverwendbare Auth-Setups für API Request Nodes.

Auth Configurations bieten wiederverwendbare Authentifizierungs-Setups für API Request Nodes. Unterstützte Authentifizierungs-Typen:

  • Bearer Token
  • Basic Auth
  • API Key
  • OAuth2 Client Credentials

Configuration

ParameterBeschreibung
NameName der Auth-Konfiguration
DescriptionOptionale Beschreibung
Auth TypeAuthentifizierungs-Methode
Secret ReferenceVerknüpftes verschlüsseltes Secret

Verhalten

  • Auth-Konfigurationen verwenden zentralisierte Secrets
  • Mehrere Workflows können dieselbe Auth-Config teilen
  • Änderungen wirken automatisch auf alle abhängigen Requests
  • Credentials werden niemals in Workflows offengelegt
Anwendung

Best Practices

Wichtigste Empfehlungen für die Verwendung des Project Settings Moduls:

  • Sensitive Daten immer als Secrets speichern
  • Shared Auth Configurations wiederverwenden
  • Keine Zugangsdaten direkt im Workflow speichern
  • Credentials pro Umgebung trennen
  • Secrets regelmässig rotieren
  • Klare Naming-Konventionen für Environments verwenden
  • OWNER-Berechtigungen auf wenige Benutzer beschränken
  • Projektzugriffe regelmässig prüfen und bereinigen
  • API Keys mit Ablaufdaten versehen
  • Separate API Keys pro Integration verwenden
