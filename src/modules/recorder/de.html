Erste Schritte

Recorder

Der Recorder ist der schnellste Weg, automatisierte Tests in Autemos zu erstellen. Statt Workflows manuell Schritt für Schritt aufzubauen, können Benutzer einfach mit der Anwendung interagieren, während Autemos sämtliche Aktionen automatisch aufzeichnet und in wiederverwendbare Test Workflows umwandelt.

Der Recorder unterstützt zwei Recording-Modi:

  • Manual Recording — klassischer Click-Recorder
  • AI Recording — KI-gestützte Testerstellung über natürliche Sprache

Während der Aufnahme erstellt Autemos automatisch Pages und Fields, Workflow Nodes, Assertions, Reusable Selectors, Page Objects sowie Tabellen- und UI-Strukturen. Der erzeugte Workflow kann anschliessend gespeichert und im Test Workflow Editor weiterbearbeitet werden.

Hauptfunktionen

Dual Recording Modes

Wählen zwischen klassischer Interaktionsaufzeichnung (Manual) und KI-gesteuerter Testerstellung über natürliche Sprache (AI).

Web & Mobile Support

Unterstützung für Browser-basierte Anwendungen sowie Mobile Automation auf Android, iOS, physischen Geräten und Device Farms.

Automatische Page Object Erkennung

Pages, Fields und Selectors werden während der Aufzeichnung automatisch erkannt und als wiederverwendbare Komponenten erstellt.

Workflow Ready

Der generierte Workflow steht sofort im Test Workflow Editor zur Weiterbearbeitung und Ausführung bereit.

Session Management

Aufnahmezustand und Sitzungsfenster

Eine neue Recorder-Session startet im Zustand Not recording. Sie bestimmen selbst, wann aufgezeichnet wird; der aktuelle Zustand ist jederzeit sichtbar.

Start, Pause, Resume

Zustand / KnopfWirkung
Not recording / Start recordingInteraktionen werden weder als Event noch als Node noch als Page-Object-Feld aufgezeichnet. Start recording schaltet auf Recording.
Recording / Pause recordingJede Interaktion erscheint in der Event-Liste. Pause recording schaltet auf Paused.
Paused / Resume recordingInteraktionen werden nicht aufgezeichnet, bisherige Einträge bleiben erhalten. Resume recording schaltet wieder auf Recording.
  • Ein gespeicherter Workflow (oder Sub-Workflow) enthält nur Schritte aus aktiven Aufnahmephasen, in zeitlicher Reihenfolge. Haben Sie vor dem Start navigiert, beginnt die Phase mit Navigate → <aktuelle URL>.
  • Auf Mobile Devices gilt dasselbe: Taps und Gesten bei Not recording oder Paused werden nicht aufgezeichnet.
  • Ein KI-Befehl bei Not recording schaltet den Zustand sichtbar auf Recording.
  • Wird gespeichert, ohne dass je gestartet wurde, lehnt der Recorder mit der Meldung „no interaction step" ab; es entsteht kein Workflow.

Live-Ansicht in einem eigenen Fenster

Bei laufender Browser- oder Mobile-Session steht über der Live-Ansicht der beschriftete Knopf Open in new window. Er liegt in einer Leiste oberhalb der Ansicht und verdeckt die getestete Anwendung nicht. Im eigenen Fenster ist das Bild grösser als eingebettet.

  • Aufnahme und Synchronität bleiben unverändert: Ein Klick im abgekoppelten Fenster erscheint im Events-Tab des Autemos-Fensters; Stop, Save und die Tabs bleiben im Autemos-Fenster bedienbar.
  • Schliessen Sie das Fenster, läuft die Session weiter. Ein Hinweis erklärt das, und der Knopf Open in new window steht wieder zur Verfügung.
  • Blockiert der Browser das Pop-up, weist ein Hinweis auf den Knopf über der Ansicht hin.
  • Ohne laufende Session gibt es den Knopf nicht.

Verlust der Browser-Session

Bricht die Browser-Session einer Web-Aufnahme weg (zum Beispiel weil der Browser extern beendet wurde), erkennt der Recorder das innerhalb von etwa 15 Sekunden von selbst:

  • In der Browserfläche erscheint die Meldung Browser session disconnected mit der Ursache und dem Knopf Start a new session, der den Add-Session-Dialog öffnet.
  • Der Tab zeigt einen roten Punkt („Disconnected"); die Aufnahme dieser Session wird kontrolliert beendet. Bei der letzten lebenden Session steht der Zustand auf Not recording, und Start recording ist gesperrt, bis wieder eine lebende Session existiert.
  • Leben weitere Tabs, läuft die Aufnahme dort unverändert weiter.
  • Der KI-Chat erhält genau einen Hinweis. Bereits aufgezeichnete Schritte, Events, Nodes und Page Objects bleiben unverändert erhalten.

Session Management

Web-Aufnahme: Tasten, Checkboxen, Dialoge und Tabs

Der manuelle Web-Recorder zeichnet neben Klicks und Eingaben auch folgende Interaktionen auf; sie werden bei der Wiedergabe (Playwright und Selenium) ausgeführt.

Tasten und Tastenkombinationen

  • Steuertasten wie Enter, Escape, Tab, Pfeiltasten oder F5 und Kombinationen wie Strg+A werden als Press Key-Node aufgezeichnet (zum Beispiel Control+a).
  • Enter in einem Suchfeld ohne Formular ergibt zuerst den Type-Node mit dem Text, danach Press Key Enter auf demselben Element. Enter in einem Formularfeld ergibt genau einen Press-Key-Node; Enter oder Leertaste auf einem Button ergibt nur den Click-Node.
  • Normales Tippen (auch mit Shift), Backspace und Delete im Feld erzeugen keine Press-Key-Nodes.

Checkbox und Radio

Das Anhaken einer Checkbox oder die Wahl eines Radio-Buttons wird als Check-Node mit dem Sollzustand aufgezeichnet (an oder aus, Label Check "<Text>"), nicht als Klick. Bei der Wiedergabe wird nur geklickt, wenn der Zustand vom Sollzustand abweicht. Ist er bereits wie gewünscht, ist der Schritt bestanden (Log „bereits gesetzt"). Damit bleibt die Checkbox auch bei mehrfacher Wiedergabe angehakt. Weicht der Zustand nach dem Klick ab, schlägt der Schritt mit Messwerten fehl.

Bestehende Workflows mit Klick-Nodes auf Checkboxen laufen unverändert.

Rich-Text-Felder

Eingaben in editierbare Bereiche (contenteditable) werden als Type-Node mit dem eingegebenen Text aufgezeichnet; die Wiedergabe füllt das Element.

Browser-Dialoge

Dialoge vom Typ alert, confirm, prompt und beforeunload werden aufgezeichnet und bei der Wiedergabe als Handle Dialog-Node ausgeführt (Aktion zum Beispiel accept, optional mit erwartetem Dialogtext).

  • Beim Aufnehmen bleibt der Dialog im Browserbild stehen, bis Sie ihn beantworten. Die Aufnahme enthält genau einen Klick und ein Dialog-Event mit Typ, Text und Entscheidung.
  • Im KI-Recorder funktioniert ein Satz wie „And I accept the confirm dialog" ebenso: Hinter dem Klick entsteht ein Handle-Dialog-Node.
  • Ein Dialog ohne Handle-Dialog-Node wird weiterhin abgelehnt. Der Node trägt jetzt aber eine Warnung mit Dialogtyp und -text; die KI erhält einen Hinweis, den Dialog mit dem passenden Werkzeug zu behandeln.

Neue Tabs und Popups

Öffnet ein Klick einen neuen Tab oder ein Popup (target=_blank, window.open), werden Klicks im neuen Tab ebenfalls aufgezeichnet. Der Workflow enthält einen Switch Tab-Node für den Wechsel und bei Bedarf einen Close Tab-Node. Ein typischer Ablauf: Klick, Switch Tab (latest), Titel prüfen, Close Tab, weiter im ursprünglichen Tab.

💡Nicht unterstützt sind Datei-Auswahl-Dialoge (dafür gibt es den Upload-Node), Basic-Auth-Prompts und Druckdialoge. Der Mobile Recorder hat eigene Alert-Semantik und ist nicht betroffen.
Session Management

Eigene Aktionen während eines KI-Zugs

Arbeitet die KI gerade und Sie klicken oder tippen selbst im Live-Bild (Browser oder Mobile Device), wird Ihre Aktion als eigener Node aufgezeichnet. Die Aktionen der KI selbst werden dabei nie doppelt aufgenommen.

  • Entscheidend ist, von wem eine Aktion stammt (KI oder Mensch), nicht wann sie geschieht. Ein Tap oder eine Eingabe von Hand im Mobile-Live-Bild ergibt genau einen Click- bzw. Type-Node, auch während eines laufenden KI-Zugs und kurz danach.
  • Ein Klick im Browserbild während eines KI-Zugs ergibt nach dem Zug genau einen Eintrag bzw. Node. Das Echo einer Aktion der KI wird nie zum Node.
  • Handgesten werden im Chat als manuelle Beobachtung vermerkt; Aktionen der KI nicht.

KI-Aufnahme im Detail

Implementationsplan und Schrittprüfung

Der AI Recorder zerlegt Ihren Auftrag in einen Implementationsplan. Der Plan erscheint im Chat und im Tab Plan der Seitenleiste. Jeder Schritt hat einen Status und, wo möglich, ein prüfbares Ziel.

Prüfung der Schritte

  • Bei verbundenem Mobile Device bekommt jeder prüfbare Schritt ein Ziel: Eine Eingabe wird über den Feldwert geprüft, ein Tap, der den Bildschirm wechselt, über ein Merkmal des nächsten Bildschirms. Der letzte Tap und der Schritt „connect mobile device" bleiben ohne Ziel.
  • Ein Schritt, dessen Ziel schon vor der Handlung galt, zählt als „done, but NOT verified", wenn er eine echte Handlung ist. Reine Prüf- und Warteschritte mit bereits geltendem Ziel zählen als verifiziert.
  • Nicht prüfbare Schritte (zum Beispiel das Verbinden des Geräts) erscheinen im Plan-Bericht getrennt und neutral statt in der Zahl „NOT verified". Ein Bericht lautet dann zum Beispiel „6 of 7 steps verified" plus eine Angabe für den nicht prüfbaren Schritt.
  • Auf dem Gerät prüft der Server das Ziel nach jeder Handlung selbst, ohne dass die KI es melden muss. Ist das Ziel erreicht, wird der Schritt abgeschlossen, bevor die nächste Handlung ans Gerät geht.
  • Ein Tap auf ein Element ausserhalb des sichtbaren Bereichs scrollt selbst herein (in beide Richtungen, begrenzt auf höchstens 10 Wischbewegungen). Ist das Element nicht erreichbar, endet der Schritt mit „element not visible" statt mit einem Tap.

Nicht ausführbare Schritte

Ist ein Schritt in der laufenden Session nicht ausführbar, wird er als Lücke not recorded festgehalten, mit dem Grund und der nächstbesten Alternative (Chat und Plan). Der Plan läuft mit den übrigen Schritten weiter. Die Schlussmeldung Plan finished listet alle Lücken („Not recorded: step N …") und alle Fehlschläge („Failed: step N …"). Stellt die KI statt einer Handlung eine Rückfrage, wird der Schritt zur Lücke mit der Rückfrage als Grund.

Mehrere Geräte im Plan

  • In einer Aufnahme über mehrere Geräte (Browser und Telefon oder zwei Telefone) wird jeder Schritt auf dem Gerät ausgeführt und geprüft, zu dem er gehört. Browser-Schritte führen nie ein Mobile-Werkzeug aus.
  • Der Chat-Plan hängt an jede Zeile „· on <Gerät>", im Tab Plan zeigt jeder Schritt „Device: <Gerät>". Bei Aufnahmen mit nur einem Gerät erscheint kein Kennzeichen.

Weiter ab hier

Nach dem Ende eines Zugs zeigt jede Plan-Karte mit Status failed, Lücke oder offen (nach einem abgebrochenen Plan) den Knopf Continue from here. Er setzt die Aufnahme an diesem Schritt fort: Schritte davor bleiben, der gewählte und alle folgenden Schritte laufen erneut. Es entsteht kein neuer Plan, die bisherigen Nodes bleiben erhalten. Der Knopf fehlt während eines laufenden Zugs, bei offener Rückfrage und bei veraltetem Plan.

Zusätzlich gilt auf dem Mobile Device: Solange ein Schritt noch geprüft wird, lässt der Recorder keine Handlung für ein fremdes Ziel durch („Report step N first"). Wartet eine Rückfrage auf Ihre Entscheidung, zeigt der Schritt „halted — waiting for your decision".

Plan-Haltepunkt

Ein Szenario-Schritt wie And I pause for review wird zum Plan-Schritt: Die Aufnahme hält an, die Karte zeigt den Stand (erledigt, pausiert, verbleibend) und die Knöpfe Continue und Stop recording.

KI-Aufnahme im Detail

Rückfragen und Sitzungsmodus

Weicht die Aufnahme vom Plan ab, hält der AI Recorder an und fragt nach, statt still weiterzulaufen. Während der Pause findet kein KI-Aufruf statt.

Session mode

Auf der Recorder-Seite wählen Sie über die Optionsgruppe Session mode zwischen Interactive (Vorgabe) und Unattended.

ModusVerhalten bei Fristablauf ohne Antwort
InteractiveDie Aufnahme stoppt; der Entwurf wird als unvollständig markiert („The draft is incomplete from step N"). Die Karte kündigt an, in wie vielen Sekunden die Aufnahme stoppt.
UnattendedDie Aufnahme läuft weiter; jede automatische Entscheidung wird im Chat protokolliert („Auto-decision at step N …").
  • Eine Antwort gilt für dieselbe Ursache bis zum Ende der Aufnahme; der Chat vermerkt „applied your earlier decision". Plan-Haltepunkte fragen immer; Stop wird nie zur Regel.
  • Vor „Save as workflow" zeigt der Dialog Review adjustments before saving alle Angleichungen (Schritt, Grund, erwartet, aufgezeichnet, wer). Ein unvollständiger Entwurf zeigt „incomplete from step N" und trägt „Incomplete from step N." in der Beschreibung.
  • Gehört eine Handlung zu einem späteren Planschritt, wird sie diesem gutgeschrieben; im Modus Interactive hält die Aufnahme vorher mit dem Grund „action belongs to step K" an.

Gescheiterte Handlung

Scheitert ein Tap, Klick oder eine Eingabe, hält die Aufnahme an und fragt mit den Knöpfen Retry, Skip step, Pick another element und Stop recording. Der Fragetext nennt Schritt, Ziel und die sichtbaren Aufschriften sowie den Grund (nicht gefunden, nicht sichtbar, schreibgeschützt, ohne Wirkung).

  • Gibt es ein passendes Element auf dem Bildschirm, fragt der Recorder schon nach dem ersten Fehlschlag (mit bis zu vier Kandidaten als Knöpfe). Sonst unternimmt die KI genau einen eigenen Neuversuch und fragt nach dem zweiten.
  • Skip step markiert den Schritt als übersprungen („Skipped by user"); die Aufnahme geht mit dem nächsten weiter. Stop recording beendet die Aufnahme, Browser bzw. Gerät werden frei, Aufgezeichnetes lässt sich speichern.
  • Pick another element führt die Handlung auf dem gewählten Kandidaten oder einer getippten Aufschrift aus.
  • Während der Pause zeigt der Kopf „Paused - waiting for you", der Tab einen Warn-Punkt, und die gescheiterte Handlung steht als roter (nicht gespeicherter) Node auf der Leinwand.
  • Antworten Sie nicht innerhalb der Frist, stoppt die Aufnahme (Speichern bleibt möglich). Sie läuft nie ungefragt weiter.
  • Meldet die KI für einen Handlungsschritt „failed" oder „not possible", kommt dieselbe Rückfrage statt eines stillen Weitermachens.

Näherungstreffer: „Did you mean …?"

Weicht das Zielelement auf dem Mobile Device nur näherungsweise vom Szenariotext ab (zum Beispiel „Software version" statt „Software information"), fragt der Recorder vor der Handlung im Chat „Did you mean “Software information”?" mit Knöpfen. Nach Ja wird genau eine Handlung auf dem tatsächlichen Element ausgeführt; Plan-Schritt und Node tragen den echten Text. Der Chat meldet Step n updated: “…” → “…”, und der Speicherdialog zeigt die Zeile unter Adjusted during recording. Mit Skip step wird nichts angetippt, mit No, let me describe it tippen Sie die Aufschrift selbst ein.

  • Unterschiede in Gross-/Kleinschreibung, Satzzeichen oder Leerraum lösen keine Frage aus. Bei Gegenbeispielen wie „Sign in" gegen „Sign out" oder „Delete" gegen „Delete all" wird immer gefragt, nie automatisch getippt.
  • Im Web-Recorder gilt dieses Verhalten nicht.

Eindeutige Fälle entscheidet der Recorder selbst

Scheitert eine Handlung nur, weil die KI das falsche Selektor-Attribut gewählt hat, und es gibt genau ein passendes Element mit derselben Aufschrift, führt der Recorder die Handlung darauf ohne Rückfrage aus. Der Chat vermerkt das, zum Beispiel Step 9: used 'Name' (same label; the AI's selector was wrong …). Bei mehreren gleichnamigen Elementen, bei nicht anklickbaren Elementen oder bei Näherungstreffern fragt der Recorder weiterhin nach.

Rotes Ziel und unbekannte Variable (Mobile)

In mobilen Aufnahmen läuft der Plan nie über einen roten Schritt hinweg. Ist ein Ziel aus Ihrem Auftrag nach der Handlung nicht erreicht, oder ist eine Variable unbekannt oder mehrdeutig, hält der Recorder mit einer Rückfrage an (Retry, Pick, Skip, Stop; bei Variablen mit den bekannten Namen als Knöpfen). Selbst erfundene oder abgeleitete Ziele („About phone screen" statt „About phone") lösen keine Frage aus, sondern werden tolerant verglichen. Im Modus Interactive erscheint auch dann eine Rückfrage-Karte, wenn die KI ohne Handlung stehen bleibt; sie zitiert die betroffene Szenariozeile.

KI-Aufnahme im Detail

Variablen, Platzhalter und Prüfungen

Variablen-Tab

Sobald die KI die erste Variable belegt (zum Beispiel mit „extract into a variable"), erscheint in der rechten Seitenleiste der Tab Variables mit einem Badge für die Anzahl. Vorher gibt es den Tab nicht.

  • Die Tabelle (nur lesen) hat die Spalten Name, Value, Source und When. Nicht leere Werte haben einen Kopier-Knopf.
  • Ein Klick auf die Quelle springt in den Tab Workflow und wählt den Extract-Node aus.
  • Der neueste Wert steht oben mit dem Badge latest. Setzt die KI dieselbe Variable erneut, ersetzt die neue Zeile die alte.
  • Im Chat steht neben dem Satz Stored "…" from "…" in <name>. der Knopf View variables, der den Tab öffnet.
  • Eine neue Aufnahme oder Clear leert die Variablen; der Tab verschwindet.

Extract: leere Werte und Belege

  • Ein leerer Wert gilt nicht mehr als Erfolg (Ausnahme: das Attribut value). Eine Warnung im Chat nennt die Variable: <variable> is empty - "<source>" had no readable text.
  • Jeder gespeicherte oder verwendete Wert wird im Chat belegt: Stored "<value>" from "<source>" in <variable>. bzw. Creating contact "<value>" (from <variable>).
  • Ein Selektor, der einen Text ausserhalb des Bildschirms festschreibt, wird vor dem Aufruf abgelehnt statt in ein Zeitlimit zu laufen.
  • Trägt ein Extract-Selektor beim Speichern den soeben ausgelesenen Wert als Bedingung (following-sibling::*[@text='12']), ersetzt der Recorder sie durch eine strukturelle Form (following-sibling::*[1]) und zeigt am Node eine Warnung. So liest der Workflow auf anderen Geräten oder in anderen Zuständen den Wert neu aus.

Platzhalter

  • Ein Werkzeugaufruf mit einem unaufgelösten Platzhalter ({{…}} oder ${…}) wird nie ausgeführt, in keinem Werkzeug und in keinem Parameter. Das gilt auch für unbekannte {{secret.X}} (Hinweis auf die Liste der Secrets) und nicht berechenbare Ausdrücke. Der Schritt wird rot, die Meldung nennt den Variablennamen, es entsteht kein Node.
  • Eine ähnliche Schreibweise einer bekannten Variable ({{androidVersion}} für android_version) wird eindeutig aufgelöst; der Node trägt {{android_version}}.
  • window.print() und File-Picker über „execute script" werden abgewiesen, ohne die Session zu gefährden.

Prüfarten für Assertions

Die KI kann zusätzlich zu positiven Prüfungen folgende Assertions aufzeichnen; im Node-Editor sind die Bedingungen sichtbar und wählbar.

PrüfartWebMobile
Element nicht sichtbar / nicht vorhandenjaja
Text nicht im Element enthalten / nicht auf der Seitejaja
Selektor nicht vorhandenjaja
URL enthält / URL gleich, Seite geladenjanein

URL- und Seitenprüfungen sowie „Text nicht auf der Seite" brauchen einen erwarteten Wert und werden sonst bei der Aufnahme abgelehnt. Negativ-Prüfungen werden bei der Wiedergabe nicht selbstgeheilt. In einer reinen Mobile-Session kann die KI ausserdem den Wert eines Elements in eine Workflow-Variable lesen („Extracted <variable> = <Wert>"), die ein Folgeschritt verwendet.

KI-Aufnahme im Detail

Jira/Xray-Testfälle aufnehmen

Wählen Sie einen Jira/Xray-Testfall (Cucumber-Szenario oder manuelle Schritte), arbeitet der AI Recorder ihn ab.

  • Implementationsplan: Der Testfall wird wie getippter Text in einen Plan zerlegt. Der Tab Plan öffnet sich von selbst; der Tab Test case bleibt erreichbar. Jeder Planschritt nennt seine Testfall-Zeile („Test case step k"). Testfall-Zeilen ohne Planschritt nennt eine Chatzeile unter dem Plan; passt die Zeilenzahl nicht, steht dort, dass die Liste nicht automatisch abgehakt wird. Ergibt die Zerlegung keinen Plan, läuft der Testfall wie bisher.
  • Abhaken: Die Liste Test case wird abgehakt, sobald alle Planschritte einer Zeile fertig sind. Zusätzlich hakt der Recorder einen Schritt selbst ab, wenn eine erfolgreiche Eingabe genau dem zitierten Wert dieses Schritts entspricht, auch wenn die KI den Schritt nicht meldet. Ein Schritt ohne tatsächliche Handlung gilt nie als erledigt, und der Zähler fällt nie.
  • Wertetreue: Getippte Werte werden gegen das Drehbuch des Testfalls geprüft. Ein Wert, der dort nicht vorkommt, wird sofort mit VALUE MISMATCH und den Werten des Testfalls abgewiesen. Richtige Werte (auch unzitierte Testdaten der manuellen Schritte) laufen; {{secret.…}} nur, wenn das Drehbuch Secrets erwähnt. Von Ihnen selbst getippte Chat-Nachrichten werden nicht geprüft.
  • Voraussetzung oder Handlung: Bei jedem Schritt erklärt die KI, ob er eine Handlung ist oder ein Zustand (im Chat „Step N: action" bzw. „checking state"). Ein Zustand wird nur geprüft und nie hergestellt; eine Handlung wird ausgeführt und aufgezeichnet. Meldet die KI einen Zustandsschritt als failed oder not possible, muss sie einen Grund nennen; er erscheint im Schritt-Panel als „failed — reported by the AI".
  • Ein selbst getippter Abbruchwunsch wird nicht durch den Testfall-Anstoss überstimmt.
Mobile Aufnahme

Mobile: Apps und mehrere Geräte

Kein App-Name: das Gerät allein

Nennt Ihr Auftrag keine App („open android"), startet die KI nur das Gerät (Home-Screen) und nicht mehr eine Standard-Demo-App. Sie weist in einem Satz darauf hin und bietet an, eine App zu nennen.

Vorinstallierte Apps und mehrere Apps

  • Ein Szenario kann mit einer vorinstallierten App beginnen (Einstellungen, Kontakte, Galaxy Store, Play Store) und im Verlauf in eine zweite App wechseln. Die App wird über ihr Paket gestartet; Apps aus dem Anbieter-Katalog funktionieren wie bisher.
  • Dafür stehen die Nodes Open App und Terminate App zur Verfügung; ein Schritt wie „open the contacts app" ist ein ausführbarer Plan-Schritt. Der Workflow läuft auf demselben Gerät durch.
  • Scheitert die Session (zum Beispiel weil eine Katalog-App fehlt oder das Gerät belegt ist), nennt die Schlusszeile im Chat den Grund des Anbieters in einem Satz. Zugangsdaten erscheinen dort nie.

Zweites Handy in derselben Aufnahme

Ist das erste Handy über den Geräte-Tab gebunden, kann die KI ein weiteres Gerät zusätzlich öffnen oder umschalten (open_mobile_device bzw. switch_session mit UDID). Alle folgenden Schritte laufen auf diesem Gerät, das erste bleibt offen.

  • Für ein bereits gebundenes Gerät meldet die KI „already connected" (kein doppelter Aufbau). Für ein nicht geöffnetes Gerät verweist switch_session auf open_mobile_device.
  • Stop bzw. Schliessen trennt nur die von der KI geöffneten Handys; das Gerät aus dem Geräte-Tab bleibt der Oberfläche.
  • Ein von der KI geöffnetes Handy hat keinen eigenen Live-View-Tab. Bedienung und Prüfung laufen über die KI-Aufnahme.
Mobile Aufnahme

Mobile: Gesten und Geräte-Aktionen

Scrollen, Wischen, Long-Press

Mobile Aufnahmen (KI und manuell) zeichnen diese Gesten als je einen Node ohne feste Bildschirmkoordinaten auf; die Wiedergabe führt sie auf jedem Gerät unabhängig von der Auflösung aus.

  • Scroll to: „scroll until I see About phone" ergibt einen Node mit Text oder XPath. Gibt es das Ziel nicht, endet der Schritt nach der festgelegten Höchstzahl an Wischbewegungen oder bei unverändertem Bildschirm mit einer Meldung, die Ziel und Wischanzahl nennt; der Node ist failed, es gibt keinen Endlos-Lauf.
  • Swipe: Richtung, Element (Wischen innerhalb eines Elements, zum Beispiel eines Karussells) und Prozent statt Pixel.
  • Long Press: „I long press on About phone" ergibt einen Long-Press-Node mit Selektor und Dauer (mindestens 500 ms). Im manuellen Recorder wird ein Halten der Maus ab 600 ms zu einem Long-Press-Schritt; ein kurzer Klick bleibt ein Tap, Ziehen bleibt ein Swipe.
  • Ältere Workflows mit Swipe-Nodes laufen unverändert.

Geräte-Aktionen

Der KI-Recorder und der manuelle Mobile Recorder zeichnen folgende Aktionen auf und spielen sie ab:

AktionVerhalten
Rotate deviceDreht das Gerät (siehe unten).
App in den Hintergrund„put the app in the background for 3 seconds and bring it back": ein Node mit Sekundenangabe; danach ist die App wieder im Vordergrund.
Deep LinkÖffnet einen Link in der App; auf Android ohne App-Paket erscheint eine verständliche Fehlermeldung.
Tastatur schliessenBlendet die Tastatur aus; ohne offene Tastatur ist der Schritt trotzdem grün.
SystemdialogNimmt einen Dialog wie „Allow location access" an oder lehnt ihn ab. Optional: Ohne Dialog wird der Schritt bei der Wiedergabe übersprungen, der Lauf bleibt grün.

Start mit frischer AppDie Session startet ohne gespeicherten Zustand (Android zusätzlich ohne App-Daten); der Erststart-Bildschirm erscheint. Vorgabe bleibt: Zustand behalten.

Rotate device

  • Der Knopf Rotate device schaltet das Gerät des aktiven Mobile-Tabs zwischen Hoch- und Querformat um; die Live Device View zieht nach.
  • Die Drehung erscheint als Schritt „Rotate LANDSCAPE" bzw. „Rotate PORTRAIT" und wird beim Speichern zu einem Rotate-Node. Bei zwei Mobile-Tabs dreht sich nur das Gerät des aktiven.
  • Dreht sich das Gerät nicht (zum Beispiel Home-Screen oder App mit fester Ausrichtung), erscheint eine Meldung mit Grund („The device did not rotate: …"); es wird kein Schritt aufgezeichnet. Während einer Drehung ist der Knopf gesperrt.

Keyboard

  • Der Keyboard-Knopf der Live Device View blendet die Bildschirmtastatur der aktiven Session ein und aus und zeigt ihren Zustand am Knopf (gedrückt = Tastatur offen). Nach einem Tap in ein Eingabefeld springt der Knopf innerhalb von etwa 20 Sekunden von selbst auf „offen".
  • Ohne aktives Eingabefeld erscheint der Hinweis „No active input field …", bei fehlender Unterstützung „… not supported on this device.".
  • Die Live Device View zeigt nach dem Umschalten sofort den neuen Bildschirm. Aufgezeichnet wird nur das Ausblenden, nicht das Einblenden.
  • Background, Deep link und System dialog treffen ebenfalls die aktive Session und melden Erfolg oder Fehler sichtbar („No system dialog found on the device." wenn kein Dialog da ist).

Aufgezeichnete Daten

Automatische Page Object Erkennung

Eine der wichtigsten Funktionen des Recorders ist die automatische Erstellung von Page Objects. Autemos erkennt während der Aufnahme kontinuierlich UI-Strukturen und erstellt daraus wiederverwendbare Komponenten.

Automatisch erkannte Elemente

  • Pages, Fields, Buttons, Inputs, Links
  • Tabellen und UI-Strukturen
  • Assertions und Selectors

Reuse Detection

Autemos erkennt automatisch bereits existierende Elemente und markiert sie als Reused oder New — Duplikate werden vermieden, die Wartbarkeit verbessert.

Pages-Tab — erkannte Page Objects und Fields, markiert als Reused oder New.

Vorhandene Page Objects zur Seite

Im Pages-Tab zeigt der Bereich Existing page objects for this page, welche Page Objects und Felder es zur geöffneten Seite bereits gibt, mit allen Feldnamen und ohne Aufklappen. Der Bereich folgt der aktuellen URL; gibt es zur Seite nichts, steht dort „No existing page objects for this page." Bei einer Mobile-Session mit App-Paket zeigt er die Page Objects dieser App; ohne Paket bzw. Bundle-ID erscheint „No app context …". Auch die KI kann die vorhandenen Page Objects zu einer Seite abfragen.

Wiederverwendung über den Selektor

Alle Recorder (KI, passiv, Auto-Mapping) verwenden ein vorhandenes Feld mit gleichem Selektor wieder, statt es unter einem neuen Namen anzulegen; der Workflow-Node verweist auf das vorhandene Feld. Der passive Recorder benennt eine Aufnahme auf einer URL mit genau einem vorhandenen Page Object nach diesem.

Vorhandene Felder beim Öffnen prüfen

Öffnet die KI eine Seite oder App, zu der Page Objects existieren, werden alle gespeicherten Selektoren in einem einzigen lesenden Durchgang live geprüft (höchstens etwa 2 Sekunden, ohne die Seite zu verändern). Jedes Feld erhält einen Befund: confirmed (genau ein sichtbarer Treffer), not found oder ambiguous (n). Bestätigte Felder übernimmt die KI unverändert, neue Selektoren baut sie nur für nicht bestätigte Elemente. Das spart Fehlversuche an veralteten Feldern. Bei veralteten Feldern erscheint pro Seitenöffnung genau eine Chat-Notiz „not found". Wird das Zeitlimit überschritten, steht „not checked live (timeout)" und die Aufnahme läuft ohne Fehler weiter.

Selektor-Reparatur

Bevor ein vorhandenes Feld einen neuen Selektor bekommt, wird der gespeicherte Selektor live geprüft. Trifft er, bleibt er stehen. Trifft er nicht, wird er überschrieben und die Reparatur gemeldet: Der Bereich Selector repairs nennt Feld, alten und neuen Selektor und die betroffenen Workflows. Konnte nicht live geprüft werden (keine Session), steht dort „(not checked live)"; eine Überschreibung geschieht nie still.

Automatische Page-Screenshots

Legt der Web-Recorder (passiv oder KI) eine Page an, die noch keinen Screenshot hat, wird im Hintergrund automatisch ein Screenshot der aufgenommenen Seite hinterlegt, in derselben Ablage wie ein manueller Upload (Bild und Vorschau werden wie beim Upload verkleinert und komprimiert).

  • Ein vorhandener Screenshot, manuell oder automatisch, wird nie überschrieben. Auch vorhandene Pages ohne Bild, die eine Aufnahme wieder verwendet, bekommen eines. Ein späterer manueller Upload ersetzt das automatische Bild.
  • Bei mehrseitigen Aufnahmen zeigt jede Page ihre eigene Seite. Navigiert die Aktion weg, entsteht kein falsches Bild; es wird bei der nächsten Zuordnung nachgeholt.
  • Die Aufnahme wird dadurch nicht langsamer. Schlägt der Screenshot fehl, bricht weder Aufnahme noch Speichern ab, und es erscheint kein Fehler.
  • Mobile-Aufnahmen und die Workflow-Ausführung lösen keinen Screenshot aus.

Änderungen im Pages-Tab speichern

Was Sie im Pages-Tab ändern (Feld oder Seite umbenennen, Selektor, Feldtyp), landet beim Speichern in den Page Objects des Projekts, bei jeder Aufnahmeart: manuell Web, reine KI-Web, Mobile und gemischt. Der gespeicherte Workflow verweist anschliessend auf die neuen Namen, die Änderung ist in der Page-Object-Verwaltung sichtbar.

  • Save All im Pages-Tab funktioniert auch ohne manuelle Web-Session und zeigt „Saved".
  • Scheitert das Speichern der Page Objects beim Speichern des Workflows, ist der Workflow trotzdem gespeichert; der Chat meldet „Pages were not stored: …".
  • Ohne Ihre Änderung entsteht beim Speichern weder ein zusätzliches Feld noch ein zusätzliches Page Object.
  • Die Selektor-Eingabe gibt es nur für bearbeitbare Felder. Bereits im Projekt vorhandene Page Objects lassen sich hier nicht umbenennen; Remove wirkt nur auf die Aufnahme, nicht auf das Page Object.

Sofort aufnehmen

AktionWirkung

Ausgabe & Integration

Was beim Speichern geschieht

Bestehende Sub-Workflows erkennen

Deckt die aufgenommene Schrittfolge einen bestehenden Sub-Workflow des Projekts vollständig ab, ersetzt der Recorder sie beim Speichern durch einen Call Sub-Workflow-Node. Das gilt auch für im Editor gebaute Sub-Workflows und auch dann, wenn der AI Recorder eigene Prüfschritte dazwischen eingeschoben hat.

  • Die aufgezeichneten Werte werden den Input-Parametern zugeordnet (zum Beispiel username = aufgezeichneter Wert). Lässt sich ein Parameter nicht eindeutig zuordnen, bleibt das Mapping leer und der Inspector des Nodes zeigt einen Hinweis mit Confirm; nach Bestätigen oder Ändern verschwindet er.
  • Secrets ({{secret.*}}) im Sub-Workflow verhindern die Erkennung nicht; der Klartext der Aufnahme landet nicht im Call-Node.
  • Beim Aufnehmen in einen bestehenden Workflow werden nur Sub-Workflows ohne Session-Start eingesetzt.
  • Kein Fehltreffer: bei anderer URL, anderem Kanal oder einem nicht-Echo-Assert dazwischen bleibt es bei den einzelnen Schritten. Teilfolgen eines Sub-Workflows werden nicht ersetzt, bereits gespeicherte Workflows werden nicht nachträglich umgebaut.

Neue KI-Konversation beginnt leer

Beginnen Sie nach dem Ende einer KI-Konversation (Stop) mit dem nächsten Befehl eine neue, startet der AI Recorder mit einer leeren Knotenliste. Der Tab Workflow und jeder Speicherweg enthalten nur die Nodes der neuen Konversation, und der Variablen-Tab enthält keine Variablen der vorigen. Waren noch ungespeicherte Schritte da, steht im Chat eine Zeile, dass sie verworfen wurden. Innerhalb derselben Konversation (weitere Befehle, Pause/Weiter) wird nichts geleert. „Stop, dann Speichern" ohne neuen Befehl speichert weiterhin die Nodes der gestoppten Konversation.

Als Test Workflow oder Sub-Workflow speichern

Beim Speichern einer Recording Session kann gewählt werden, ob die aufgezeichneten Schritte als Test Workflow oder als Sub-Workflow abgelegt werden.

Ein Sub-Workflow eignet sich, wenn der aufgezeichnete Prozess in mehreren Tests verwendet werden soll, nur einen Teil eines vollständigen Tests darstellt, wiederverwendbare Eingabeparameter benötigt oder zentral gepflegt werden soll. Weitere Wege zur Erstellung beschreibt Sub-Workflow erstellen und extrahieren.

Sub-Workflow speichern: Input-Parameter

Der Speicherdialog einer neuen Aufnahme zeigt die Optionen Workflow (vorgewählt) und Sub-workflow. Bei Workflow gibt es keinen Parameter-Schritt; gespeichert wird wie bisher mit Start-Node vorn und Close Browser hinten.

Bei Sub-workflow erscheint die Gruppe Input parameters mit Add parameter. Je Zeile geben Sie Parameter name, Default value und Required an; Remove parameter löscht die Zeile.

  • Leere, ungültige oder doppelte Parameternamen werden an der Zeile gemeldet; Save bleibt dann gesperrt.
  • Der Sub-Workflow hat keinen Start-Node, dafür einen Kopf-Node, der die Parameter deklariert, und alle aufgezeichneten Schritte. Ein Close Browser wird nicht automatisch angehängt; ein aufgezeichneter bleibt.
  • Das gilt für alle Speicherwege (KI, Handaufnahme Web und Mobile). Aufgezeichnete Werte werden dabei nicht automatisch durch {{Parametername}} ersetzt.
  • Der Sub-Workflow erscheint in der Workflow-Liste als Subworkflow und lässt sich in anderen Workflows über Call Sub-Workflow wählen; seine Parameter erscheinen dort als Inputs. Erfolgsmeldungen nennen „sub-workflow".
  • Beim Fortsetzen eines bestehenden Workflows (Edit live from here) gibt es diese Wahl nicht.
