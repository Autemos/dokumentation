Getting Started

Recorder

The Recorder is the fastest way to create automated tests in Autemos. Instead of building workflows manually step by step, users can simply interact with the application while Autemos automatically captures every action and turns it into reusable test workflows.

The Recorder supports two recording modes:

  • Manual Recording — classic click recorder
  • AI Recording — AI-assisted test creation through natural language

During recording, Autemos automatically creates Pages and Fields, Workflow Nodes, Assertions, Reusable Selectors, Page Objects as well as table and UI structures. The generated workflow can then be saved and further edited in the Test Workflow Editor.

Key Features

Dual Recording Modes

Choose between classic interaction recording (Manual) and AI-driven test creation through natural language (AI).

Web & Mobile Support

Support for browser-based applications as well as mobile automation on Android, iOS, physical devices and device farms.

Automatic Page Object Detection

Pages, Fields and Selectors are automatically detected during recording and created as reusable components.

Workflow Ready

The generated workflow is immediately available in the Test Workflow Editor for further editing and execution.

Session Management

Recording State and Session Window

A new Recorder session starts in the Not recording state. You decide when recording begins; the current state is visible at all times.

Start, Pause, Resume

State / buttonEffect
Not recording / Start recordingInteractions are recorded neither as events, nor as nodes, nor as Page Object fields. Start recording switches to Recording.
Recording / Pause recordingEvery interaction appears in the event list. Pause recording switches to Paused. The button is disabled while the AI is working or a question is open.
Paused / Resume recordingInteractions are not recorded; existing entries are kept. Resume recording switches back to Recording.
  • A saved workflow (or sub-workflow) contains only steps from active recording phases, in chronological order. If you navigated before starting, the phase begins with Navigate → <current URL>.
  • The same applies on mobile devices: taps and gestures while Not recording or Paused are not recorded.
  • An AI command while Not recording visibly switches the state to Recording.
  • If you save without ever having started, the Recorder refuses with the message "no interaction step"; no workflow is created.

Live View in Its Own Window

While a browser or mobile session is running, a labelled Open in new window button sits above the live view. It is placed in a bar above the view and does not cover the application under test. In its own window the image is larger than when embedded.

  • Recording and synchronisation are unchanged: a click in the detached window appears in the Events tab of the Autemos window; Stop, Save and the tabs remain usable in the Autemos window.
  • If you close the window, the session keeps running. A notice explains this, and the Open in new window button is available again.
  • If the browser blocks the pop-up, a notice points to the button above the view.
  • Without a running session, there is no button.

Loss of the Browser Session

If the browser session of a web recording is lost (for example because the browser was closed externally), the Recorder normally detects it by itself within about 15 seconds:

  • The browser area shows the message Browser session disconnected with the cause and the Start a new session button, which opens the Add Session dialog.
  • The tab shows a red dot ("Disconnected"); recording for this session ends in a controlled way. For the last live session, the state switches to Not recording and Start recording stays locked until a live session exists again.
  • If other tabs are alive, recording there continues unchanged.
  • The AI chat receives exactly one notice. Steps, events, nodes and Page Objects recorded so far remain unchanged.

Every recorded action becomes a node in the visual workflow.

Session Management

Web Recording: Keys, Checkboxes, Dialogs and Tabs

Besides clicks and inputs, the manual web recorder also captures the following interactions; they are executed on replay (Playwright and Selenium).

Keys and Key Combinations

  • Control keys such as Enter, Escape, Tab, arrow keys or F5 and combinations such as Ctrl+A are recorded as a Press Key node (for example Control+a).
  • Enter in a search field without a form produces the Type node with the text first, then Press Key Enter on the same element. Enter in a form field produces exactly one Press Key node; Enter or Space on a button produces only the Click node.
  • Normal typing (also with Shift), Backspace and Delete inside a field do not produce Press Key nodes.

Checkbox and Radio

Ticking a checkbox or choosing a radio button is recorded as a Set Checkbox node with the target state (on or off, step name Check "<text>" or Uncheck "<text>"), not as a click. On replay a click only happens if the state differs from the target state. If it is already as desired, the step passes (log "already set"). This keeps the checkbox ticked even when the recording is replayed repeatedly. If the state still differs after the click, the step fails with measured values.

Existing workflows with Click nodes on checkboxes run unchanged.

Rich-Text Fields

Input into editable areas (contenteditable) is recorded as a Type node with the entered text; replay fills the element.

Browser Dialogs

Dialogs of type alert, confirm, prompt and beforeunload are recorded and executed on replay as a Handle Dialog node (action such as accept, optionally with expected dialog text).

  • While recording, the dialog stays in the browser image until you answer it. The recording contains exactly one click and one dialog event with type, text and decision.
  • The AI Recorder handles a sentence such as "And I accept the confirm dialog" the same way: a Handle Dialog node is created after the click.
  • A dialog without a Handle Dialog node is still dismissed. The node now carries a warning with the dialog type and text; the AI receives a hint to handle the dialog with the matching tool.

New Tabs and Popups

If a click opens a new tab or popup (target=_blank, window.open), clicks in the new tab are recorded as well. The workflow contains a Switch Tab node for the switch and, if needed, a Close Tab node. A typical flow: click, Switch Tab (latest), check the title, Close Tab, continue in the original tab.

💡File-selection dialogs (use the Upload node), basic-auth prompts and print dialogs are not supported. The Mobile Recorder has its own alert semantics and is not affected.
Session Management

Your Own Actions During an AI Turn

If you click or type in the live view (browser or mobile device) while the AI is working, your action is recorded as a node of its own. The AI's own actions are never recorded twice.

  • What counts is who performed an action (AI or human), not when it happens. A tap or input made by hand in the mobile live view produces exactly one Click or Type node, even during a running AI turn and shortly afterwards.
  • A click in the browser image during an AI turn produces exactly one entry or node after the turn. The echo of an AI action never becomes a node.
  • Hand gestures are noted in the chat as a manual observation; AI actions are not.

AI Recording in Detail

Implementation Plan and Step Verification

The AI Recorder breaks your task down into an implementation plan. The plan appears in the chat and in the Plan tab of the side panel. Each step has a status and, where possible, a verifiable goal.

Verifying Steps

  • With a connected mobile device, every verifiable step gets a goal: an input is verified through the field value, a tap that changes the screen through a feature of the next screen. The last tap and the "connect mobile device" step stay without a goal.
  • A step whose goal already held before the action counts as "done, but NOT verified" if it is a real action. Pure check and wait steps with an already-true goal count as verified.
  • Steps that cannot be verified (for example connecting the device) appear separately and neutrally in the plan report instead of in the "NOT verified" count. A report then reads, for example, "6 of 7 steps verified" plus a note for the step that cannot be verified.
  • On the device, the server verifies the goal itself after every action, without the AI having to report it. Once the goal is reached, the step is completed before the next action reaches the device.
  • A tap on an element outside the visible area scrolls it into view by itself (in both directions, limited to at most 10 swipes). If the element cannot be reached, the step ends with the message "ELEMENT_NOT_VISIBLE … is outside the viewport and could not be scrolled into view" instead of a tap.

Steps That Cannot Be Executed

If a step cannot be executed in the running session, it is recorded as a gap, not recorded, with the reason and the next best alternative (chat and plan). The plan continues with the remaining steps. The closing message Plan finished lists all gaps ("Not recorded: step N …") and all failures ("Failed: step N …"). If the AI asks a question instead of acting, the step becomes a gap with the question as the reason.

Several Devices in the Plan

  • In a recording across several devices (browser and phone, or two phones), every step is executed and verified on the device it belongs to. Browser steps never run a mobile tool.
  • The chat plan appends "· on <device>" to each line; in the Plan tab each step shows "Device: <device>". Recordings with only one device show no marker.

Continue from Here

After a turn ends, every plan card with status failed, gap or open (after an aborted plan) shows the Continue from here button. It resumes recording at that step: earlier steps stay, the chosen step and all following steps run again. No new plan is created, and existing nodes are kept. The button is absent during a running turn, with an open question, and with an outdated plan.

On a mobile device the following also applies: while a step is still being verified, the Recorder does not let an action for a different target through ("Report step N first"). While a question waits for your decision, the step shows "halted — waiting for your decision".

Plan Breakpoint

A scenario step such as And I pause for review becomes a plan step: recording stops, the card shows the status (done, paused, remaining) and the buttons Continue and Stop recording.

AI Recording in Detail

Questions and Session Mode

If the recording deviates from the plan, the AI Recorder stops and asks instead of silently continuing. No AI call takes place during the pause.

Session mode

In the header of the AI Chat, the Session mode option group lets you choose between Interactive (default) and Unattended.

ModeBehaviour when the time limit passes without an answer
InteractiveRecording stops; the draft is marked incomplete ("The draft is incomplete from step N"). The card announces in how many seconds recording stops.
UnattendedRecording continues; every automatic decision is logged in the chat ("Auto-decision at step N …").
  • An answer applies to the same cause for the rest of the recording; the chat notes "applied your earlier decision". Plan breakpoints always ask; Stop never becomes a rule.
  • Before "Save as workflow", the dialog Review adjustments before saving shows all adjustments (step, reason, expected, recorded, by whom). An incomplete draft shows "incomplete from step N" and carries "Incomplete from step N." in its description.
  • If an action belongs to a later plan step, it is credited to that step; in Interactive mode, recording first stops with the reason "action belongs to step K".

Failed Action

If a tap, click or input fails, recording stops and asks with the buttons Retry, Skip step, Pick another element and Stop recording. The question names the step, the target and the visible labels, as well as the reason (not found, not visible, read-only, no effect).

  • If a matching element is on the screen, the Recorder asks after the first failure (with up to four candidates as buttons). Otherwise the AI makes exactly one retry of its own and asks after the second failure.
  • Skip step marks the step as skipped ("Skipped by user"); recording continues with the next one. Stop recording ends the recording, the browser or device is released, and what was recorded can be saved.
  • Pick another element performs the action on the chosen candidate or on a label you type.
  • During the pause the header shows "Paused - waiting for you", the tab shows a warning dot, and the failed action appears as a red (unsaved) node on the canvas.
  • If you do not answer within the time limit, recording stops (saving remains possible). It never continues unasked.
  • If the AI reports "failed" or "not possible" for an action step, the same question appears instead of silently moving on.

Near Matches: "Did you mean …?"

If the target element on the mobile device deviates from the scenario text only approximately (for example "Software version" instead of "Software information"), the Recorder asks in the chat before acting: "Did you mean “Software information”?" with buttons. After Yes, exactly one action is performed on the actual element; plan step and node carry the real text. The chat reports Step n updated: “…” → “…”, and the save dialog shows the line under Adjusted during recording. With Skip step nothing is tapped; with No, let me describe it you type the label yourself.

  • Differences in capitalisation, punctuation or whitespace do not trigger a question. For counter-examples such as "Sign in" versus "Sign out" or "Delete" versus "Delete all", the Recorder always asks and never taps automatically.
  • This behaviour does not apply to the web recorder.

Unambiguous Cases Are Decided by the Recorder

If an action fails only because the AI chose the wrong selector attribute, and there is exactly one suitable element with the same label, the Recorder performs the action on it without asking. The chat notes this, for example Step 9: used 'Name' (same label; the AI's selector was wrong …). With several elements of the same name, with non-clickable elements or with near matches, the Recorder still asks.

Red Goal and Unknown Variable (Mobile)

In mobile recordings, the plan never moves past a red step. If a goal from your task is not reached after the action, or a variable is unknown or ambiguous, the Recorder stops with a question (Retry, Pick, Skip, Stop; for variables with the known names as buttons). Invented or derived goals ("About phone screen" instead of "About phone") do not trigger a question; they are compared tolerantly. In Interactive mode a question card also appears when the AI stops without acting; it quotes the affected scenario line.

AI Recording in Detail

Variables, Placeholders and Checks

Variables Tab

As soon as the AI assigns the first variable (for example with "extract into a variable"), the Variables tab appears in the right side panel with a count badge. Before that, the tab does not exist.

  • The table (read-only) has the columns Name, Value, Source and When. Non-empty values have a copy button.
  • Clicking the source jumps to the Workflow tab and selects the Extract node.
  • The newest value is on top with the badge latest. If the AI sets the same variable again, the new row replaces the old one.
  • In the chat, the sentence Stored "…" from "…" in <name>. has a View variables button that opens the tab.
  • A new recording or Clear empties the variables; the tab disappears.

Extract: Empty Values and Evidence

  • An empty value no longer counts as success (exception: the attribute value). A chat warning names the variable: <variable> is empty - "<source>" had no readable text.
  • Every stored or used value is evidenced in the chat: Stored "<value>" from "<source>" in <variable>. or Creating contact "<value>" (from <variable>).
  • A selector that hard-codes text that is not on the screen is rejected before the call instead of running into a timeout.
  • If an Extract selector carries the value that was just read as a condition when saving (following-sibling::*[@text='12']), the Recorder replaces it with a structural form (following-sibling::*[1]) and shows a warning on the node. This way the workflow re-reads the value on other devices or in other states.

Placeholders

  • A tool call with an unresolved placeholder ({{…}} or ${…}) is never executed, in no tool and no parameter. This also applies to unknown {{secret.X}} (with a pointer to the list of secrets) and expressions that cannot be calculated. The step turns red, the message names the variable, and no node is created.
  • A similar spelling of a known variable ({{androidVersion}} for android_version) is resolved unambiguously; the node carries {{android_version}}.
  • window.print() and file pickers through "execute script" are rejected without endangering the session.

Assertion Types

In addition to positive checks, the AI can record the following assertions; the conditions are visible and selectable in the node editor.

Check typeWebMobile
Element not visible / does not existyesyes
Text not contained in element / not on the pageyesyes

URL and page checks as well as "text not on the page" need an expected value and are otherwise rejected during recording. Negative checks are not self-healed on replay. In a pure mobile session, the AI can also read the value of an element into a workflow variable ("Extracted <variable> = <value>") that a following step uses.

AI Recording in Detail

Recording Jira/Xray Test Cases

If you select a Jira/Xray test case (Cucumber scenario or manual steps), the AI Recorder works through it.

  • Implementation plan: The test case is broken down into a plan just like typed text. The Plan tab opens by itself; the Test case tab remains reachable. Each plan step names its test case line ("Test case step k"). Test case lines without a plan step are named in a chat line below the plan; if the line count does not match, it states that the list is not ticked off automatically. If the breakdown yields no plan, the test case runs as before.
  • Ticking off: The Test case list is ticked off as soon as all plan steps of a line are finished. In addition, the Recorder ticks off a step itself when a successful input exactly matches the quoted value of that step, even if the AI does not report the step. A step without an actual action never counts as done, and the counter never decreases.
  • Value fidelity: Typed values are checked against the script of the test case. A value that does not occur there is rejected immediately with VALUE MISMATCH and the values of the test case. Correct values (also unquoted test data from the manual steps) run; {{secret.…}} only if the script mentions secrets. Chat messages you type yourself are not checked.
  • Precondition or action: For each step the AI declares whether it is an action or a state (in the chat "Step N: action" or "checking state"). A state is only checked and never produced; an action is executed and recorded. If the AI reports a state step as failed or not possible, it must give a reason; it appears in the step panel as "failed — reported by the AI".
  • A cancel request you type yourself is not overridden by the test case prompt.
Mobile Recording

Mobile: Apps and Several Devices

No App Name: the Device Alone

If your task names no app ("open android"), the AI starts only the device (home screen) and no longer a default demo app. It points this out in one sentence and offers to name an app.

Pre-installed Apps and Several Apps

  • A scenario can begin with a pre-installed app (Settings, Contacts, Galaxy Store, Play Store) and switch to a second app along the way. The app is started via its package; apps from the provider catalog work as before.
  • The Open App and Terminate App nodes are available for this; a step such as "open the contacts app" is an executable plan step. The workflow runs through on the same device.
  • If the session fails (for example because a catalog app is missing or the device is busy), the closing line in the chat names the provider's reason in one sentence. Credentials never appear there.

Second Phone in the Same Recording

If the first phone is bound through the Device tab, the AI can additionally open or switch to another device (open_mobile_device or switch_session with a UDID). All following steps run on this device; the first stays open.

  • For an already bound device the AI reports "already connected" (no duplicate setup). For a device that is not open, switch_session points to open_mobile_device.
  • Stop or close disconnects only the phones opened by the AI; the device from the Device tab remains with the UI.
  • A phone opened by the AI has no live view tab of its own. Operation and checks run through the AI recording.
Mobile Recording

Mobile: Gestures and Device Actions

Scroll, Swipe, Long Press

Mobile recordings (AI and manual) capture these gestures as one node each without fixed screen coordinates; replay executes them on any device regardless of resolution.

  • Scroll to: "scroll until I see About phone" produces one node with text or XPath. If the target does not exist, the step ends after the defined maximum number of swipes, or when the screen stays unchanged, with a message naming target and swipe count; the node is failed, there is no endless run.
  • Swipe: direction, element (swiping within an element, for example a carousel) and percentage instead of pixels.
  • Long Press: "I long press on About phone" produces a Long press node with selector and duration (at least 500 ms). In the manual recorder, holding the mouse for 600 ms or more becomes a Long Press step; a short click stays a tap, dragging stays a swipe.
  • Older workflows with Swipe nodes run unchanged.

Device Actions

Rotate device

  • The Rotate device button toggles the device of the active Mobile tab between portrait and landscape; the Live Device View follows.
  • The rotation appears as the step "Rotate LANDSCAPE" or "Rotate PORTRAIT" and becomes a Rotate node when saved. With two Mobile tabs, only the device of the active one rotates.
  • If the device does not rotate (for example home screen or an app with fixed orientation), a message with the reason appears ("The device did not rotate: …"); no step is recorded. While a rotation is in progress, the button is locked.

Keyboard

  • The Keyboard button of the Live Device View shows and hides the on-screen keyboard of the active session and shows its state on the button (pressed = keyboard open). After a tap into an input field, the button switches to "open" by itself within about 20 seconds.
  • Without an active input field the hint "No active input field …" appears; if unsupported, "… not supported on this device.".
  • After toggling, the Live Device View immediately shows the new screen. Only hiding is recorded, not showing.
  • Background, Deep link and System dialog also hit the active session and report success or failure visibly ("No system dialog found on the device." if there is no dialog).

Recorded Data

Automatic Page Object Detection

One of the most important features of the Recorder is the automatic creation of Page Objects. During recording, Autemos continuously detects UI structures and creates reusable components from them.

Automatically Detected Elements

  • Pages, Fields, Buttons, Inputs, Links
  • Tables and UI structures
  • Assertions and Selectors

Reuse Detection

Autemos automatically recognizes already existing elements and marks them as Reused or New — duplicates are avoided and maintainability is improved.

Pages tab — detected Page Objects and Fields, marked as Reused or New.

Existing Page Objects for the Page

In the Pages tab, the On this page area (with the current URL) shows which Page Objects and fields already exist for the opened page, with all field names and without expanding. The area follows the current URL; if nothing exists for the page it reads "No existing page objects for this page." For a mobile session with an app package it shows the Page Objects of that app; without a package or bundle ID, "No app context …" appears. The AI can also query the existing Page Objects of a page.

Reuse by Selector

All recorders (AI, passive, auto-mapping) reuse an existing field with the same selector instead of creating it under a new name; the workflow node references the existing field. The passive recorder names a recording on a URL with exactly one existing Page Object after that Page Object.

Checking Existing Fields on Open

When the AI opens a page or app for which Page Objects exist, all stored selectors are checked live in a single read-only pass (about 2 seconds at most, without changing the page). Each field gets a result: confirmed (exactly one visible match), not found or ambiguous (several matches). The AI adopts confirmed fields unchanged and builds new selectors only for unconfirmed elements. This saves failed attempts on outdated fields. If fields are outdated, exactly one chat note of the form "<Page>: N of M stored fields confirmed on this page; not found: …" appears per page open; the fields are repaired when recorded. If the time limit is exceeded, recording continues without error.

Selector Repair

Before an existing field receives a new selector, the stored selector is checked live. If it matches, it stays. If it does not, it is overwritten and the repair is reported: the Selector repairs area names, per field, the old and new selector and the number of workflows that use the field ("used in N workflows"). If no live check was possible (no session), it reads "(not checked live)"; an overwrite never happens silently.

Automatic Page Screenshots

When the web recorder (passive or AI) creates a Page that has no screenshot yet, a screenshot of the recorded page is stored automatically in the background, in the same place as a manual upload (image and preview are reduced and compressed as with an upload).

  • An existing screenshot, manual or automatic, is never overwritten. Existing Pages without an image that a recording reuses also get one. A later manual upload replaces the automatic image.
  • In multi-page recordings each Page shows its own page. If the action navigates away, no wrong image is created; it is made up for at the next assignment.
  • Recording does not become slower. If the screenshot fails, neither recording nor saving is aborted, and no error appears.
  • Mobile recordings and workflow execution do not trigger a screenshot.

Saving Changes from the Pages Tab

What you change in the Pages tab (renaming a field or page, selector, field type) ends up in the project's Page Objects on save, for every recording type: manual web, pure AI web, mobile and mixed. The saved workflow then references the new names, and the change is visible in the Page Object management.

  • Save All in the Pages tab also works without a manual web session and shows "Saved".
  • If saving the Page Objects fails while saving the workflow, the workflow is saved anyway; the chat reports "Pages were not stored: …".
  • Without a change from you, saving creates neither an additional field nor an additional Page Object.
  • The selector input exists only for editable fields. Page Objects that already exist in the project cannot be renamed here; Remove affects only the recording, not the Page Object.
Output & Integration

Continuing an Existing Workflow (Edit live from here)

With Edit live from here you enter the Recorder at a node of an existing workflow: the workflow runs up to the insertion point, after which you record further steps that are inserted into the workflow.

Recording Immediately

  • As soon as the insertion point is reached, the Recorder shows "Recording" and "Pause recording" without you pressing Start recording. A click of your own in the browser image appears immediately in the Events tab in the section "Recording from here". On mobile the same applies to finger taps in the device image.
  • While the run is still travelling to the insertion point, the state stays "Not recording". A new empty session (Add session, also after Clear) starts as usual with "Not recording".
  • Pause recording and Resume recording work here as well.

Saving

The save dialog always shows the Target workflow group with name, insertion position (label and ID) and version. Next to it are two separate actions:

ActionEffect
Update workflowInserts the steps after the anchor into the existing workflow. Existing nodes and connections stay, the version increases by 1 (with snapshot). Also works if the parked run no longer has a worker session, after "Could not attach" and after Clear.
Save as new workflowCreates a new workflow from the original and the recording; the original stays unchanged.
  • The toolbar button is called Save as workflow. Finish run inserts the manual step exactly once after the anchor.
  • If you enter at the last node "Close Browser", the run parks before it, and the dialog shows "Insert before: Close Browser".
  • If someone has changed the workflow in the meantime (version conflict), the dialog stays open with a conflict notice and the two ways out.

Resuming Mobile Workflows

If you enter a mobile workflow via Edit live from here, the Live Device View shows the image of the device on which the run is standing at the insertion point. The controls of the Live Device View (tap, swipe, long press, keys such as HOME and BACK, rotate, keyboard, typing text) act on exactly this device.

  • Your own tap in the device image appears immediately in the Events tab and is inserted into the workflow exactly once behind the anchor at Finish run. Start recording is not needed for this.
  • The device belongs to the run: the Live Device View does not end its session.
  • After Finish run, after Clear and once the edit session has expired, the last image stays, the controls are hidden, and input no longer reaches the device.

Expired Edit Session

  • If the edit session has expired or ended, the Recorder says so in plain text. The save dialog stays open and the recording is preserved.
  • While the tab is open, the Recorder keeps the session alive automatically (about once a minute). If it ends anyway, a one-time notice appears in the chat.
  • Clear discards the parked run; browser and grid slot are freed.
  • Reloading or closing the tab with unsaved steps triggers the browser prompt. If you navigate away within the application, the Leave recording? dialog appears with Stay and Discard and leave. Recorded steps are not restored after a reload.
Output & Integration

What Happens on Save

Recognising Existing Sub-Workflows

If the recorded sequence of steps fully covers an existing sub-workflow of the project, the Recorder replaces it on save with a Call Sub-Workflow node. This also applies to sub-workflows built in the editor, and even if the AI Recorder inserted check steps of its own in between.

  • The recorded values are mapped to the input parameters (for example username = recorded value). If a parameter cannot be mapped unambiguously, the mapping stays empty and the node's Inspector shows a notice with Confirm; after confirming or changing it, the notice disappears.
  • Secrets ({{secret.*}}) in the sub-workflow do not prevent recognition; the plain text of the recording does not end up in the Call node.
  • When recording into an existing workflow, only sub-workflows without a session start are inserted.
  • No false matches: with a different URL, a different channel or a non-echo assert in between, the individual steps remain. Partial sequences of a sub-workflow are not replaced, and already saved workflows are not restructured afterwards.

A New AI Conversation Starts Empty

If, after an AI conversation has ended (Stop), you begin a new one with the next command, the AI Recorder starts with an empty node list. The Workflow tab and every save path contain only the nodes of the new conversation, and the Variables tab holds no variables of the previous one. If there were still unsaved steps, a line in the chat says they were discarded. Within the same conversation (further commands, pause/resume) nothing is emptied. "Stop, then save" without a new command still saves the nodes of the stopped conversation.

Output & Integration

Replay: Selection Lists and Multiple Matches

Selection lists (Select)

  • A selection in a dropdown (Playwright) fails within one time limit, no longer after two in a row. The limit is the node's timeout; if none is set, 15 seconds apply.
  • The option is chosen by value or label. If the element exists but no option matches, the error reads Option '<text>' not found; available: … with up to 10 existing labels.
  • If the element itself is missing, the previous message ("waiting for locator …") stays; optional steps are then skipped and self-healing applies as before.

Click with several visible matches

If the selector of a click (also Hover and Click) matches several visible elements, the worker clicks the one whose own text or accessible name (aria-label, title, alt) equals the text in the selector exactly (case-insensitive). If none does, the best-scored visible match applies as before. For example, "Run" is clicked rather than "More run options".

  • Recognised as text anchors are text=…, :has-text("…"), role=…[name="…"] and XPath expressions with contains(., '…'), text()='…' or normalize-space()='…'. CSS selectors, #id, [data-testid], links via href and positional selectors have no anchor; nothing changes there.

AI recording and self-healing

  • A screenshot taken by the AI no longer waits for the page to settle.
  • Self-healing sees the worker's page tree up to a length of 36,000 characters, not just an excerpt of it.

Saving as a Test Workflow or Sub-Workflow

When saving a recording session, you can choose whether the recorded steps are stored as a Test Workflow or as a Sub-Workflow.

A Sub-Workflow is suitable when the recorded process should be used in multiple tests, represents only part of a complete test, requires reusable input parameters or should be maintained centrally. See Creating and Extracting Sub-Workflows for the other creation paths.

Saving a Sub-Workflow: Input Parameters

The save dialog of a new recording shows the options Workflow (preselected) and Sub-workflow. With Workflow there is no parameter step; it is saved as before with the start node in front and Close Browser at the end.

With Sub-workflow, the Input parameters group appears with Add parameter. For each row you enter Parameter name, Default value and Required; Remove parameter deletes the row.

  • Empty, invalid or duplicate parameter names are reported on the row; Save then stays locked.
  • The sub-workflow has no start node, but a header node that declares the parameters, and all recorded steps. A Close Browser is not appended automatically; a recorded one is kept.
  • This applies to all save paths (AI, manual recording for web and mobile). Recorded values are not automatically replaced by {{parameterName}}.
  • The sub-workflow appears in the workflow list as a sub-workflow and can be chosen in other workflows via Call Sub-Workflow; its parameters appear there as inputs. Success messages mention "sub-workflow".
  • When continuing an existing workflow (Edit live from here), this choice does not exist.
