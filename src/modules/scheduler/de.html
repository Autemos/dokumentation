Scheduler

Test Scheduler

Das Test Scheduler-Modul ermöglicht Teams die Automatisierung und Orchestrierung von Testausführungen über Projekte, Workflows und Environments hinweg. Es bietet zentralisierte Planungsfähigkeiten für wiederkehrende Regressions-Suiten, Smoke Tests, Monitoring-Prüfungen und verkettete Ausführungsflüsse.

Was das Modul bietet

  • Zeitbasierte Ausführung mit Cron-Intervallen
  • Ereignisbasierte Ausführung auf Basis von Abhängigkeiten zwischen Schedules
  • Bevorstehende Ausführungen überwachen und historische Läufe prüfen
  • Ausführungseinstellungen und Environments konfigurieren
  • Schedules bei Bedarf manuell auslösen
  • Externe CI/CD-Integration via API

Scheduler

Testdaten im Zeitplan

In Create New Schedule und Edit Schedule legen Sie beim Anhaken eines Workflows direkt fest, mit welchen Testdaten er läuft — mit denselben Möglichkeiten wie beim manuellen Lauf Data-driven execution….

Auswahl im Dialog

  • Unter der Liste der Workflows erscheint für jeden angehakten Workflow ein Block Test data for «Workflow». Abhaken entfernt den Block samt Auswahl.
  • Als Modus stehen Single dataset, All datasets, Selected datasets, First N datasets und By tags zur Verfügung (Tags siehe Test Data Easy).
  • Ist die Auswahl unvollständig, bleiben Create Schedule bzw. Save Changes gesperrt.
  • Die Auswahl gilt nur für Zeitpläne mit dem Ziel Workflows, nicht für Collections. Ohne Auswahl läuft der Workflow wie bisher einmal.

Bearbeiten

Im Edit-Dialog sind die dem Zeitplan zugeordneten Tests angehakt und zeigen ihre gespeicherte Auswahl. Neu angehakte Tests werden beim Speichern hinzugefügt, geänderte Auswahlen aktualisiert. Abhaken entfernt den Test beim Speichern aus dem Zeitplan („Unchecking removes the test from this schedule when you save.“).

Detailseite und Lauf

  • Die Detailseite fasst die Auswahl je Test in einer Zeile zusammen, z. B. „Run once per dataset: First 10 datasets · Tags: Smoke · Source: Test Data Easy“.
  • Beim Lauf startet der Zeitplan einen Batch mit einem Run je Datensatz; der Run-Verlauf zeigt den Datensatz je Lauf.
  • Fehlt einem Datensatz ein vom Workflow benötigtes Feld, wird der Test mit einer Meldung als FAILED beendet, ohne dass ein Run startet.

Xray-Reporting pro Zeitplan

Jeder Workflow-Zeitplan entscheidet selbst, ob seine Ergebnisse nach Jira Xray gemeldet werden. Technische Kontrollläufe, Entwicklungstests oder häufig ausgeführte Regressionstests erzeugen so keine unnötigen Test Executions.

Einstellungen im Dialog

Der Abschnitt Reporting erscheint in Create/Edit Schedule, wenn das Projekt eine Jira-Zuordnung hat und das Ziel Workflows ist (nicht Collections).

ElementBeschreibung
Report results to Jira XraySchalter, Standard aus. Hilfetext: „Creates a new Xray test execution for every scheduled run.“ Bestehende Zeitpläne bleiben aus.
Xray Test PlanErscheint nur bei eingeschaltetem Schalter. Ein Jira-Schlüssel wie SB-381. Leer übernimmt den Test Plan, den das Projekt als Standard hinterlegt hat („Leave empty to use the project default (KEY)“). Hat das Projekt keinen Standard, ist das Feld Pflicht.
  • Gespeichert wird nur mit gültiger Konfiguration: ohne Jira-Zuordnung des Projekts erscheint „Reporting to Jira Xray needs a Jira mapping for this project.“, ohne Test Plan „A test plan is required to report results to Jira Xray. …“, bei ungültigem Schlüssel „… is not a valid Jira issue key.“
  • Ausschalten ist immer möglich. Der eingetragene Plan bleibt erhalten, wird aber nicht benutzt.

Was bei jedem Lauf passiert

Ist der Schalter an, legt Autemos nach dem Ende jedes Zeitplan-Laufs eine neue Xray Test Execution im Test Plan an. Der Titel lautet „Autemos – <Zeitplanname> – <Datum Uhrzeit> (run <Kennung>)“. Gemeldet werden die Xray-Tests, die mit den Workflows des Zeitplans verknüpft sind — in einer einzigen Anfrage mit den echten Ergebnissen. Ältere Läufe behalten ihre eigene Execution und werden nie überschrieben.

Ergebnis in AutemosStatus in XrayKommentar
bestandenPASSED—
fehlgeschlagenFAILEDFehlertext
technischer Fehler (Startfehler, Abbruch, Timeout)FAILED„Technical error: …“
nicht gelaufen (Abhängigkeit fehlgeschlagen)TODO„Not run: dependency failed“
  • Ist ein Xray-Test mit mehreren Workflows verknüpft, gilt der schlechteste Status; bei Wiederholungen zählt der letzte Versuch.
  • Der Kommentar je Test enthält den Link zum Report des Laufs.
  • Sind keine Xray-Tests verknüpft, wird nichts nach Jira gesendet.
  • Scheitert die Meldung (z. B. Jira nicht erreichbar), ändert das weder Ergebnis noch Status des Zeitplan-Laufs.
  • Die Detailseite zeigt den Stand, z. B. „Reporting to Jira Xray: On – Test Plan X (from project)“ oder „Off“.

Anwendungsfälle

External Integration

Integration

Zusätzlich zur integrierten Planung unterstützt Autemos die Integration mit externen Orchestrierungs- und CI/CD-Plattformen. Dies ermöglicht Organisationen, automatisierte Tests direkt aus bestehenden Delivery-Pipelines auszulösen.

Unterstützte Plattformen

  • GitLab CI/CD
  • Jenkins
  • Azure DevOps
  • GitHub Actions
  • Benutzerdefinierte Pipeline-Systeme via API

API-basierte Ausführung

Autemos stellt APIs bereit, die es externen Systemen ermöglichen, einzelne Tests, vollständige Workflows, Regressions-Suiten und geplante Ausführungsketten auszulösen. Externe Systeme verwalten die Orchestrierung, während Autemos Testausführung, Browser-Automation, Reporting, Self-Healing und Analyse übernimmt.

Häufige Integrationsszenarien

SzenarioAblauf
CI/CD-ValidierungGitLab Pipeline → Deployment → Autemos Tests auslösen → Validieren
Enterprise-PlanungEnterprise Scheduler → Autemos API → Automatisierte Ausführung
Release GateBuild → Deployment auf Staging → Workflow auslösen → Auswerten → Fortfahren oder Stoppen

Interne vs. externe Planung

TypBeschreibung
InternDirekt im Test Scheduler-Modul verwaltet
ExternVia API aus CI/CD- oder Enterprise-Systemen ausgelöst
💡 Viele Organisationen verwenden einen hybriden Ansatz — interne Schedules für wiederkehrendes Monitoring und Regressionstests, externe Trigger für CI/CD und Deployment-Validierung. Beides kann kombiniert werden, während die zentralisierte Berichterstattung in Autemos erhalten bleibt.
